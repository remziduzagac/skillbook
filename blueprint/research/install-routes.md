# Research: install routes and the harnesses skillbook could reach

How a collection of skill sets could be installed in each agent harness, and whether a set's hidden skills, nested in folders below its main skill, would stay hidden and reachable there. Read on 2026-10-18 for the install routes of D152, D184 and D185. Claude Code and Codex are tested in [skill-loading.md](skill-loading.md); this file covers the rest.

## How to read this file

- **Provenance:** as in the blueprint's conventions, with one addition: *inferred*, deduced from what was read, not seen. Every claim marked *summary* came from a page or a source file fetched through a small model's summary, so quotes are close, not verbatim, and line numbers were not shown. Nothing here was run, except where [skill-loading.md](skill-loading.md) is cited.
- **The questions asked of each harness:** does it have a marketplace or another way to install a collection; which folders it reads skills from; whether a skill nested below another skill's folder is found and listed; how a skill is hidden from the model's list; how skill names are kept apart; and whether skills.sh can install into it.
- **Versions:** Claude Code 2.1.302 and Codex 0.163.0 were the newest at the time; the others have no version shown by what was read.

## Summary

- **Claude Code and Codex have plugin marketplaces and need nothing else for a set;** the other harnesses differ so much that each later one needs its own handling (D184).
- **pi** has no marketplace, installs packages from npm or Git, and does not list a skill nested inside another skill's folder (its code stops at a `SKILL.md`), so a tree stays hidden there without a flag. The docs say the opposite, that skills are found recursively ([pi](#pi)).
- **Hermes Agent** lists every nested skill it finds under a skills folder, has no per-skill hide flag, and can be told to hide skills only by the person's own configuration; a plugin that registers only the main skills avoids this ([Hermes Agent](#hermes-agent)).
- **Another harness** lists nested skills too (its older code and newer docs say any depth) and hides a skill by its own metadata key, which still lets the skill be loaded by name ([Another harness](#another-harness)).
- **skills.sh** copies a skill's folder whole, nested skills included, but treats a nested `SKILL.md` as part of the shallower skill, and does not hide anything from the model's list ([skills.sh](#skillssh)).
- **Of the other harnesses,** Cursor, Factory Droid and Amp scan folders recursively; Copilot CLI reads only the immediate subfolders of a plugin's `skills/`; most of the rest say nothing about nesting ([Other harnesses](#other-harnesses)).

## skills.sh

Source: the README and `src/skills.ts` and `src/installer.ts` of vercel-labs/skills (*summary*).

- **Targets:** about 70 agents. Many share the project folder `.agents/skills/` (Amp, Cline, Codex, Cursor, Factory Droid, Gemini CLI, Copilot, pi, Kilo Code, Warp, Zed); Claude Code uses `.claude/skills/`, Goose `.goose/skills/`, Kiro `.kiro/skills/`, Roo Code `.roo/skills/`, Windsurf `.windsurf/skills/`. Global folders differ per agent.
- **How it installs:** a canonical copy in `.agents/skills/<name>`, then a symlink per agent (the default); `--copy` copies into each agent's folder, and a failed symlink falls back to a copy.
- **Whole folders:** the copy recurses and skips only `metadata.json`, `.git`, `__pycache__` and `__pypackages__`; symlinks inside are copied as content, and broken ones skipped. So a main skill's nested folders, their `SKILL.md` files included, are carried along intact.
- **Nested `SKILL.md`:** in the normal walk a `SKILL.md` below a found skill is not a skill of its own ("stopping below a discovered skill"), and a shallower one shadows what is nested below it. The recursive fallback, used when nothing was found or with `--full-depth`, does not stop at a found skill, so nested ones can then be listed as skills.
- **Finding skills:** the repository root if it has a `SKILL.md`, then `skills/`, its `.curated`, `.experimental` and `.system` folders, and about 60 agent folders, to depth 3; a fallback search to depth 5. If `.claude-plugin/marketplace.json` or `plugin.json` exists, the skills it declares are also found (`plugins[].skills`, `metadata.pluginRoot`). From this it follows, *inferred* and untested, that a plugin manifest could drive skills.sh discovery too.
- **Names:** the install folder is the sanitised `name` from the frontmatter (lowercase, odd characters to hyphens), else the folder name; duplicate names are dropped. No namespace. `metadata.internal: true` hides a skill from discovery unless `INSTALL_INTERNAL_SKILLS=1`.
- **Hiding from the model:** skills.sh does not do it; frontmatter is copied unchanged, *inferred* from the copy code, except for one agent (`eve`) whose keys are rewritten.
- **Commands:** `npx skills add` (a local folder, GitHub shorthand, Git, GitLab or Azure URLs, tree URLs, a `SKILL.md` or archive URL), `update [skills] [-g|-p] [-y]`, `list`, `find`, `remove`, `init`; flags `-l`, `-s <name>` (`'*'` for all), `--all`, `-a <agent>`, `-g`, `--copy`, `-y`, `--full-depth`. Its docs pages (`skills.sh/docs`, `/docs/cli`) are thin: install, packs, and a telemetry opt-out (`DISABLE_TELEMETRY=1`) (*summary*).
- **What it means for a tree** (*inferred*): a nested skill travels with its main skill, but a harness that scans recursively (Cursor, Factory Droid, Amp, pi's docs, Codex) lists it, while one-level harnesses (the older behaviour of one harness, a Copilot plugin) do not. Hiding nested skills therefore has to be done per harness, or by renaming the nested file. Not tested.

## Another harness

This harness's docs show two lines, called V1 and V2 here. Provenance *summary* throughout.

- **The skill's folder:** in V2, loading a skill returns its content, then "Base directory for this skill", then a note that relative paths are relative to it, then up to ten sampled supporting files (the V2 code and docs agree). The listing holds each skill's id, name and description and no path (in the V2 code); a skill is left out when it has no description, when its hide key is false or when a permission denies it. V1's code is gone from the branch (404); the only view of it was a forum summary, and whether V1 output carries the base directory is not answered by anything read.
- **Installing:** no marketplace. A plugin is a JS or TS module, listed under the config key `plugin` (V1) or `plugins` (V2) by npm name, Git spec (V2) or local folder, with a plugin add command in V2. A plugin adds skills by code: V1 pushes a folder into `config.skills.paths`, V2 calls `ctx.skill.transform()` and adds each skill. The config `skills` array (V2) takes relative, `~/` or absolute paths or HTTP catalogs, and arrays from several configs combine; a catalog is an `index.json` listing skills and files with a version, cached and fetched again when the version differs. skills.sh writes to `.agents/skills/` or to the harness's own global skills folder.
- **Several sets in one repository:** the plugin spec names a repository, with no subfolder syntax seen, so one plugin per repository, or a plugin that registers a subfolder, or a `skills` config path to any subfolder (*inferred*, the last read in the V2 docs).
- **Updates:** a Git spec resolves again only on a cache clear or a reinstall; it can be pinned with `#v7.0.0`. Plugin update commands: not stated.
- **Nested skills, the known conflict:** the V2 docs say files named exactly `SKILL.md` "can be at any depth", with the id derived from the path; the V2 scan code was not found. For V1 only a secondary forum summary exists, giving the globs `{skill,skills}/**/SKILL.md` for its own folders and `skills/**/SKILL.md` for Claude's, from its V1 skill source file, while V1's docs say "one folder per skill name". An earlier reading of its older behaviour, that it lists one level, therefore conflicts with the newer docs and with that summary, which both say any depth. Not run, so not settled; the safe reading is that a nested `SKILL.md` is probably found and listed (*inferred*) unless hidden.
- **Hiding:** a metadata key in the skill's frontmatter set to `"false"` (V1 docs); V2 also accepts `disable-model-invocation: true`, and when both are present the metadata key wins. It removes the skill from the listing, and the skill can still be loaded by its exact name. A second metadata key set to `"true"` lets the person type `/name` (V1 docs). A plain read of the file is not blocked (*inferred*); a `deny` permission blocks the skill tool.
- **Names:** V1 requires the name to equal the folder name, matching `^[a-z0-9]+(-[a-z0-9]+)*$`, unique across locations, and does not say which wins a clash. In V2 the id comes from the path, not from `name`, and later sources win in the order built-in, `.claude` and `.agents`, its global skills folder, its project skills folder, then config `skills` entries. No namespace. The superpowers notes say bundled skills win clashes on V1 1.18.31, and project over personal over plugin on V2.
- **Verdict** (*inferred*): works if every nested skill carries the hide key, loadable by name and by path; V1's behaviour should be confirmed by running it.

## pi

The repository is github.com/earendil-works/pi (the task named badlogic/pi-mono, which the docs still sit under), package `packages/coding-agent`. Provenance *summary*.

- **No marketplace.** `pi install npm:pkg@ver`, `git:github.com/x/y@ref`, a URL or a local path; `pi -e <source>` for one run; `-l` for project scope, stored in `.pi/settings.json`, else `~/.pi/agent/settings.json`. A package is described by the `pi` key in `package.json` (`extensions`, `skills`, `prompts`, `themes`, as paths and globs, with `!` excludes) or by the conventional folders `extensions/`, `skills/`, `prompts/`, `themes/`; the keyword `pi-package` lists it in the gallery. `.claude-plugin` is not mentioned. Updates by `pi update`; Git and npm refs are pinned and updates do not move them. Packages can run extension code, and the docs warn to review the source. skills.sh also works (`.agents/skills/`, `~/.agents/skills/`).
- **Several sets in one repository:** the docs do not say a subfolder can be its own package, so one package per repository, with the `skills` globs exposing chosen subfolders and per-package filters (`!pattern`, `+path`, `-path`) narrowing what loads (*inferred*). Two sets in one repository could then not be installed separately except by filters.
- **Skill folders:** `~/.agents/skills/` and `.agents/skills/` (project, searched from the working folder up to the repository root); the settings `skills` array adds paths. `.claude/skills` is not mentioned on the skills page.
- **The skill's folder:** pi has no skill tool. The system prompt lists each skill with its absolute file path (`formatSkillsForPrompt` in `src/core/skills.ts`), with the instruction to read the file when the task matches and to resolve relative paths against the skill's folder. A `/skill:name` command expands to the skill's text with "References are relative to" its base folder (`src/core/agent-session.ts`). A model that read a nested skill by path therefore knows its folder from the path it used (*inferred*).
- **Nested skills, the known conflict:** the docs say "Directories containing SKILL.md are discovered recursively" (`docs/skills.md`), but the code is stricter: `loadSkillsFromDir` treats a folder with a `SKILL.md` as a skill root and does not go further; it skips dot folders and `node_modules` and honours `.gitignore`, `.ignore` and `.fdignore`. So a `SKILL.md` inside a main skill's folder is not found or listed, in the code. If the top `SKILL.md` is ignored by an ignore rule, the search continues below it.
- **Hiding:** `disable-model-invocation: true` leaves a skill out of the prompt and keeps `/skill:name`; the setting `enableSkillCommands` controls the slash entries. The model can still read the file by path (*inferred*). With the rule above, nested skills need no flag. A nested skill can be typed only by its path, not by `/skill:` (*inferred*).
- **Names:** lowercase letters, digits and hyphens, up to 64 characters; the name need not equal the folder name, and falls back to it. On a clash the first found wins and a diagnostic `name "x" collision` is reported. No namespace for packaged skills.
- **Verdict** (*inferred*): the tree works natively and stays hidden if only main skills sit at the globbed level.

## Hermes Agent

github.com/NousResearch/hermes-agent, branch `main`. Provenance *summary*.

- **The skill's folder:** the `skill_view` tool (`tools/skills_tool.py`) returns JSON with `path` (relative to the active skills folder), `skill_dir` (absolute, or none for a flat `.md`) and `linked_files` grouped as references, templates, assets and scripts. What it returns for a plugin-registered skill was not visible. The listing in the system prompt (`agent/prompt_builder.py`) holds names, descriptions and categories, no paths.
- **Installing:** a hub: `hermes skills install owner/repo/skills/my-workflow` (a skill folder inside a repository), `official/...`, skills.sh, a well-known URL or a direct URL; taps (`hermes skills tap add owner/repo`, skill folders under `skills/` with a configurable path); `hermes skills check` and `update`. A plugin: `hermes plugins install owner/repo [--enable]`, with a `plugin.yaml` (name, version, description, capabilities, `requires_env`, `manifest_version`, `api_version`, `requires_plugins`, `update_url`) and an `__init__.py` whose `register(ctx)` calls `ctx.register_skill(name, Path)`; its skills are named `plugin:skill` and loaded by `skill_view("plugin:skill")`. `--ref` needs a full 40-character SHA; `hermes plugins update NAME` stashes local edits and reapplies them, and `check-updates` exists. A plugin in a subfolder of a repository: not stated. Extra read-only folders: `skills.external_dirs`; the project's `.hermes/skills/` and `.agents/skills/` after `hermes skills trust`.
- **Several sets in one repository:** yes through hub and tap paths (`owner/repo/skills/<set>`); whether a whole nested folder is copied was not verified in the source (*inferred*: whole).
- **Nested skills:** `iter_skill_index_files` (`agent/skill_utils.py`) walks the folders with `os.walk(followlinks=True)`, prunes excluded folders and, in a folder that has a `SKILL.md`, the names references, templates, assets and scripts. It does not stop at a `SKILL.md`, so nested skills at any depth are found and listed, under a category taken from the first path part when the path has three or more; a same-level name clash lists the relative path as the name; lookup by name has no depth limit. Through the plugin route only registered skills are listed, so a tree stays hidden there (*inferred*) and reading by path works.
- **Hiding:** no per-skill frontmatter flag in the docs. The person's configuration has `skills.disabled` and `skills.platform_disabled`, which hide a skill from the catalog and make `skill_view` refuse it with "disabled ... inspect files directly on disk"; `platforms:` and `metadata.hermes` fields (`requires_toolsets`, `fallback_for_*`) hide by environment. A package cannot set the configuration; `requires_tools: [nonexistent]` could hide a skill (*inferred*, hacky). The model can still read files with `read_file`, as superpowers' bootstrap tells it.
- **Names:** plugin skills are `plugin:skill` and never collide with local names. Local precedence: project, local, `create_dir`, `external_dirs`, higher shadowing lower.
- **A learning loop that edits skills:** `skill_manage` (`tools/skill_manager_tool.py`) creates, patches, writes and removes files in, and deletes skills; its docstring says existing skills, bundled, hub or user, "are modified in place", found in the local folder and then in `skills.external_dirs`, with no read-only check in that file. Plugin-registered skills are not mentioned by `_find_skill`, so probably not editable that way (*inferred*). A background review, a fork roughly every ten turns, "can patch, rewrite, and add support files to any skill it learns from", bundled and hub skills included (the curator docs). The curator manages only agent-created skills; hub skills are off-limits to it and bundled ones are never patched.
- **Holding it off:** `skills.write_approval: true` stages changes in `~/.hermes/pending/skills/` for `/skills approve`; `hermes curator pin <skill>` (the docs conflict on whether a pinned skill can still be patched); `curator.enabled: false` and `hermes curator pause`. Skills in `skills.external_dirs` are "externally owned: autonomous lifecycle maintenance treats them as read-only" (`is_external_skill_path`), yet `skill_manage`'s schema says external ones are modified where they live; which wins for edits is unclear. No per-folder or per-skill read-only flag was found.
- **Updates and edits:** bundled skills use an origin-hash manifest, and user-modified ones are skipped on update forever unless `reset` or `--restore`; a plugin update reapplies local edits; a hub update's behaviour with edits is not stated.
- **Verdict** (*inferred*): install as a plugin that registers each main skill, or by the hub path; the folder is known through `skill_dir`. The risk is the learning loop patching installed skills, mitigated by `skills.write_approval` or a pin, both the person's settings.

## How superpowers packages for these harnesses

github.com/obra/superpowers, version 7.0.0 in `package.json`, a collection with one level of skills in `skills/` (*summary*).

- **Layout:** `.pi/extensions/superpowers.ts`, `.hermes-plugin/`, `.claude-plugin`, `.codex-plugin` and others side by side, with `package.json` holding `main` for the other harness and a `pi` key (`extensions`, `skills: ["./skills"]`).
- **Another harness:** a plugin file in its plugins folder; on V1 a `config` hook pushes the skills folder into `config.skills.paths`, on V2 `setup(ctx)` scans `skills/<name>/SKILL.md` (one level) and adds each through `ctx.skill.transform()`. It also adds a start-of-session text to the first user message, skipped for child sessions. Installed by a Git spec in `plugin` or `plugins`, pinned with `#v7.0.0`; no files are copied.
- **pi:** `pi install git:github.com/obra/superpowers`; `pi.skills` registers the folder, and an extension hooks resource discovery, session start, compaction, the end of an agent turn and context, to insert the start text. It adds no tools.
- **Hermes Agent:** `hermes plugins install obra/superpowers --enable`; `register(ctx)` loops one level of `skills/*/SKILL.md` and calls `ctx.register_skill(name, Path(skill_md), description=...)` (a plain string silently disables the plugin); a `pre_llm_call` hook adds the start text on the first turn. The text says to load with `skill_view("superpowers:skill-name")`, falling back to reading the file by path. Files are registered by path, not copied.
- **Notable:** it registers one level only, so it does not test nested trees.
