# A quiet health issue keeps repositories green

greenrepo's single "Repository health" issue is the right surface for a solo maintainer with a personal GitHub account, but only if it is built like Renovate's Dependency Dashboard rather than like a weekly report: **one issue found by a label, rewritten only when its content changes, opening with the date of its last run, listing only lines someone can act on, and keeping accepted deviations apart** so nothing stays red forever. No large project in the sample (uv, rust-lang/rust, deno, cli/cli) pins a bot-written health issue; they keep *state* in a dashboard and send *events*, such as a flaky test or a failed run, to their own issues, labels or chat, and greenrepo should adopt that split. The weekly workflow became much easier to build on **2026-09-03, when `GITHUB_TOKEN` gained read access to Dependabot alerts**: a collector made of `gh` and `jq`, with read-only job permissions, now gathers nearly every signal, free on public repositories and for roughly 1–2% of the Free plan's minutes on private ones. What CI still cannot read with its own token (secret scanning alerts, security and Actions settings, merge settings, deploy keys, secret ages) is exactly the sensitive part, and it is better read monthly in the person's own agent session than through a stored admin-read token or written into a public issue. Settings drift on a personal account has no native detection and no tool that fits cleanly, so greenrepo needs a committed expected-settings file that the workflow diffs and reports, never applies. For agents, the safe default is a session the person starts, which reads the issue and proposes; a scheduled CI agent earns its place only behind a deterministic no-op gate, with a read-only agent job, structured output and one narrow write, because injected issue and comment text made the Claude, Gemini, Codex and Copilot agents leak secrets in published 2025–2026 research, with CVEs assigned to Claude Code and Gemini CLI. The last section turns this into twelve concrete edits to greenrepo's UPK, CI, AGT and SET rules.

## Mature projects keep state in a dashboard and events in their own issues

The closest precedent for greenrepo's proposal is Renovate's Dependency Dashboard, one bot-owned issue rewritten on every run. Renovate's GitHub code looks the issue up by exact title, closes any other open issue with the same title as a duplicate, compares title, body and state with the server's copy, returns "Issue is open and up to date - nothing to do" when they match, and otherwise patches the body and **reopens the issue if a person closed it** ([Renovate GitHub platform code](https://github.com/renovatebot/renovate/blob/main/lib/modules/platform/github/index.ts)). Checkboxes in the body work as commands, each keyed by a hidden comment such as `<!-- unschedule-branch=renovate/msrv -->`, so the person approves a pending update by ticking a box ([Renovate dashboard code](https://github.com/renovatebot/renovate/blob/main/lib/workers/repository/dependency-dashboard.ts)). astral-sh/uv's dashboard shows how the pattern ages: created 2024-03-25 and still rewritten on 2026-10-10, it has no comments, is **not among uv's three pinned issues**, and opens with "This PR body was truncated due to platform limits" ([astral-sh/uv#2658](https://github.com/astral-sh/uv/issues/2658)).

For events, the same projects do something else. uv dispatches a Codex agent on a failed run; the agent must classify the failure as `flaky` or `deterministic` and decide `create`, `duplicate` or `ignore`, flaky runs are retried up to three times, and real failures become issues in a separate repository, `astral-sh/uv-dev`, under a prompt that says "Do not create an issue merely because a pull request is red" ([uv diagnose-workflow-failure.yml](https://github.com/astral-sh/uv/blob/main/.github/workflows/diagnose-workflow-failure.yml); [uv prompt](https://github.com/astral-sh/uv/blob/main/agents/prompts/diagnose-workflow-failure.md)). rust-lang/rust tracks spurious CI failures with label families such as `CI-spurious-fail-msvc` and a meta tracking issue ([rust-lang/rust#133959](https://github.com/rust-lang/rust/issues/133959)), and its pinned slots hold feature tracking issues and draft release notes. deno uploads its daily compatibility results to S3, posts to Slack, and opens no issue at all ([deno node_compat_test workflow](https://github.com/denoland/deno/blob/main/.github/workflows/node_compat_test.generated.yml)). githubnext's `repo-status` agentic template opens a new `[repo-status]` issue every day and closes the older ones ([agentics repo-status.md](https://github.com/githubnext/agentics/blob/main/workflows/repo-status.md)), and Allstar opens **one issue per violated policy**, comments on it every 24 hours while the violation lasts, and closes it automatically once the violation is fixed ([ossf/allstar](https://github.com/ossf/allstar)).

GitHub's own surfaces give a personal account less than the headline features suggest. Security overview exists only for organisations and enterprises ([GitHub Docs: security overview](https://docs.github.com/en/code-security/security-overview/about-security-overview)); code scanning on private repositories needs GitHub Code Security, which is sold for organisation-owned repositories on Team and Enterprise ([GitHub docs source: code scanning availability](https://github.com/github/docs/blob/main/data/reusables/gated-features/code-scanning.md)); and the community profile is a file checklist for public repositories, not a health score ([GitHub Docs: community profiles](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories)). What does reach a solo maintainer is Dependabot's alert notifications, including a daily or weekly digest email "for up to 10 of your repositories" ([GitHub Docs: Dependabot notifications](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/configuring-notifications-for-dependabot-alerts)), and Actions failure notifications, which for scheduled workflows go to the user who created the workflow or last edited its cron line ([GitHub Docs: workflow notifications](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs)). Neither reaches an agent, which reads issues, not email. CHAOSS supplies vocabulary rather than a surface, and two of the four metrics in its Starter Project Health model degenerate for one person: the contributor absence factor is always one, and time to first response is meaningful only when activity is "primarily driven by humans, not automated responses" ([CHAOSS Starter Project Health](https://chaoss.community/kb/metrics-model-starter-project-health/)).

The verdict is that greenrepo's single issue is sound for **state** and wrong for **events**. Open alerts, switched-off schedules, credentials near expiry and failing rules are facts that hold or do not hold this week, and one stable page that the person and every agent read is the right home for them, all the more on an account with no security overview. A flaky test or a broken release is different: it needs a discussion, a fix and a closing, which is why every mature project gives it its own issue, and why greenrepo's QA-09 already asks for an issue link when a test is quarantined. The case for agentics' issue-per-run is a clean history and a notification on every run; for one person, a weekly notification that says nothing new is noise, and a label lookup finds the current page either way. The health issue should therefore list state and link to per-problem issues, the way Renovate's dashboard links to its pull requests.

### Design the issue to stay quiet, current and trusted

Identity comes from a dedicated label, `repository-health`, plus a marker in the body, not from the title, so a person who retitles the issue does not cause a second one; the collector closes duplicates and reopens the issue if it was closed, as Renovate does. The body is written **only when the rendered text differs from the stored one**, so a quiet week produces no edit and no event. Its first line gives the date of the last run and a link to the run. That line is the dead-man's switch: a disabled or crashed collector cannot report itself, so each agent session treats a last run older than about eight days as a red item of its own. Edits are also silent; an old and unofficial report says GitHub sends no notification when a description is edited ([isaacs/github#310](https://github.com/isaacs/github/issues/310)), which current documentation neither confirms nor denies. The collector should therefore add **one comment when a critical item first appears** (a new critical Dependabot alert, a credential due within seven days, a schedule switched off) and stay silent otherwise. Agents should read the body, not the comments, because cli/cli found that comments hidden in the web interface still come back through the REST API, so an agent that re-reads its own history pays more on every run ([cli/cli dependabot-triage.md](https://github.com/cli/cli/blob/trunk/.github/workflows/dependabot-triage.md)).

The body is ordered by who must act: what needs the person (merge the grouped dependency pull request, renew a token, decide about a manually disabled workflow), what an agent can propose (a failing link check, a new unpinned action, an issue without an end state), the accepted deviations, and the signals not available on this repository, with long informational lists collapsed in `<details>`. Lists need caps and links to their evidence, because Renovate truncates its dashboard to the platform's maximum body length and uv's dashboard already carries the truncation notice. A hidden machine block such as `<!-- greenrepo-health v1 {...} -->` can store last week's failing rules, so "newly failing" becomes a diff with no cache or artifact. That block is for the collector only: claude-code-action strips HTML comments from what the model sees ([claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)), and two layers of GitHub Agentic Workflows strip them too, which once broke cli/cli's deduplication and made its bot "re-comment on every run" ([cli/cli dependabot-triage.md](https://github.com/cli/cli/blob/trunk/.github/workflows/dependabot-triage.md)). Anything an agent must act on, checkbox keys included, belongs in visible text.

Permanent red trains the reader to skip the page. Scorecard's own documentation says small projects "with only one active participant" cannot meet Contributors, and that for a low Maintained score "There is no remediation work needed" ([Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md)). Such items belong in an **accepted list with a reason and a review date**, the way OSV-Scanner ignores a non-affecting vulnerability in `osv-scanner.toml` with its ID and a reason ([Scorecard checks: Vulnerabilities](https://github.com/ossf/scorecard/blob/main/docs/checks.md#vulnerabilities)), and Scorecard appears as per-check changes, never as a score. herdsman shows why the list must exist: its live settings, read through the API on 2026-10-10, show Dependabot security updates disabled ([herdsman](https://github.com/remziduzagac/herdsman)), which greenrepo's DEP-01 asks to be on but which the fork's practice of taking Rust updates with each base release may justify. Without an accepted list, that line is red every week whether or not anyone intends to change it.

On a public repository the issue is world-readable, and Dependabot alerts are delivered only to people with write, maintain or admin access ([GitHub Docs: Dependabot notifications](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/configuring-notifications-for-dependabot-alerts)). A public health issue therefore shows alert counts with a link to the Security tab, never package names or paths, and secret scanning alerts do not appear in it at all, which keeps it within greenrepo's AGT-04. The body also mixes facts the bot computed with strings outsiders control: Dependabot pull request titles, package names, error messages and link URLs. The collector renders those in code spans and strips `@` mentions, the agents treat them as data, and locking the issue's conversation keeps outside comments off the page agents read. Pinning is a convenience for the person, not the issue's identity. A repository has only **three pin slots** ([GitHub Docs: pinning an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/pinning-an-issue-to-your-repository)), user-facing notices deserve them first on a repository with users, and uv leaves its own dashboard unpinned. The REST API has no endpoint for pinning issues; GraphQL's `pinIssue` and `gh issue pin` exist, but whether `GITHUB_TOKEN` may call them is unconfirmed, so the person pins the issue once by hand.

## Since September 2026, the workflow's own token reads nearly every signal

The permission that changes the design is `vulnerability-alerts`, added to `GITHUB_TOKEN` on 2026-09-03 with only `read` and `none` as values ([GitHub Changelog](https://github.blog/changelog/2026-09-03-github-actions-early-september-2026-updates/)). Before it, Dependabot alerts needed a personal access token or an App. GitHub's docs now draw the line explicitly: `security-events: read` lists code scanning alerts, Dependabot alerts use the new permission, and "Secret scanning alerts cannot be read with this permission and require a GitHub App or a personal access token" ([GitHub docs source: token permissions](https://github.com/github/docs/blob/main/data/reusables/actions/github-token-scope-descriptions.md)). Listing any permission sets every unlisted one to `none`. One caveat is real: the docs flag for the permission was committed in April and the changelog came in September, which suggests a staged rollout, and nobody in this research ran a workflow that uses it on a personal-account repository.

The table maps each signal greenrepo's UPK-04 names to its endpoint and the narrowest credential that reads it, from GitHub's machine-readable permission map ([fine-grained permission map](https://github.com/github/docs/blob/main/src/github-apps/data/fpt-2022-11-28/fine-grained-pat-permissions.json)). "Any token" means the endpoint needs only `metadata: read`, which every token has; "absent on private" means the feature does not exist on a personal account's private repositories.

| Signal | Endpoint | Read with | Note |
| --- | --- | --- | --- |
| Dependabot alerts | `dependabot/alerts` | `vulnerability-alerts: read` | new on 2026-09-03 |
| Dependabot pull requests | `pulls` | `pull-requests: read` | filter on the author |
| Issues without an end state | `issues` | `issues: read` | avoid the search API |
| Failed scans and link checks | `actions/workflows/{file}/runs` | `actions: read` | latest conclusion |
| Schedules switched off | `actions/workflows` | `actions: read` | `state` field |
| Rulesets | `rulesets` | any token | private needs Pro |
| Private vulnerability reporting | `private-vulnerability-reporting` | any token | public only |
| Code scanning alerts | `code-scanning/alerts` | `security-events: read` | absent on private |
| Secret scanning alerts | `secret-scanning/alerts` | PAT or App, admin user | absent on private |
| Security toggles, Actions policy | `security_and_analysis` and others | `administration: read` | not `GITHUB_TOKEN` |
| Merge settings | the repository object | `contents: write` | not worth granting |
| Deploy keys, secret ages | `keys`, `actions/secrets` | `administration`, `secrets` | not `GITHUB_TOKEN` |
| Token expiry | a response header | the calling token only | renewals file |

Three rows need comment. Code scanning returns `404 {"message":"no analysis found"}` on herdsman because none is configured, so the collector must read that as "not configured", not as an error. Secret scanning alerts also require that "the authenticated user must be an administrator for the repository" ([GitHub REST: secret scanning](https://docs.github.com/en/rest/secret-scanning/secret-scanning#list-secret-scanning-alerts-for-a-repository)), and on user-owned private repositories the feature exists only under Enterprise Cloud with managed users or on GitHub Enterprise Server ([GitHub docs source: secret scanning availability](https://github.com/github/docs/blob/main/data/reusables/gated-features/secret-scanning.md)), while Dependabot alerts are available for user-owned repositories ([GitHub docs source: Dependabot alerts availability](https://github.com/github/docs/blob/main/data/reusables/gated-features/dependabot-alerts.md)). The security block of the repository object is visible only to admins, and "To view merge-related settings, you must have the `contents:read` and `contents:write` permissions" ([GitHub REST: get a repository](https://docs.github.com/en/rest/repos/repos#get-a-repository)), a write grant no health collector should hold.

Expiry is mostly unreadable. The deploy key schema has `created_at`, `last_used` and `read_only` but **no expiry field** ([GitHub REST: deploy keys](https://docs.github.com/en/rest/deploy-keys/deploy-keys)); listing personal access tokens exists only under `/orgs/` ([GitHub REST: organisation PATs](https://docs.github.com/en/rest/orgs/personal-access-tokens)); and the only expiry the API reveals is that of the token making the request, through the `GitHub-Authentication-Token-Expiration` header ([GitHub Changelog 2021-07-26](https://github.blog/changelog/2021-07-26-expiration-options-for-personal-access-tokens/)), which in September 2025 returned a time one minute in the future on REST for some fine-grained tokens ([community discussion 172213](https://github.com/orgs/community/discussions/172213)). GitHub emails renewal reminders to the account and revokes tokens unused for a year ([GitHub Docs: token expiration](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)), but neither reaches an agent. The workable answer is a **renewals file** in the repository, listing each credential and renewal with its kind, where it lives, its expiry or rotation date and the action due, which the collector reads and flags within a set number of days, enriched with deploy-key `last_used` and secret `updated_at` where a session can read them.

Schedules are the one signal the workflow can repair as well as report. GitHub disables scheduled workflows in a public repository after 60 days without activity, and the workflow list reports them as `disabled_inactivity`, distinct from `disabled_manually` ([GitHub REST: workflows](https://docs.github.com/en/rest/actions/workflows); [GitHub Docs: schedule event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)). The enable endpoint needs only `actions: write`, and liskin/gh-workflow-keepalive "uses GitHub API to preemptively re-enable the workflow, thus preventing it from being automatically disabled" without dummy commits ([liskin/gh-workflow-keepalive](https://github.com/liskin/gh-workflow-keepalive)). The best-known commit-based alternative, gautamkrishnar/keepalive-workflow, has returned "Repository access blocked" for terms-of-service reasons since 2025-04-21 ([gautamkrishnar/keepalive-workflow](https://github.com/gautamkrishnar/keepalive-workflow)), so dummy commits are out. GitHub does not define "repository activity", so the collector must not assume its own issue edits count. The rule that follows: the health workflow re-enables itself on every run, in a job that runs even when collection fails; it re-enables any scheduled workflow GitHub switched off for inactivity, because that restores a decision the person already made; and it only reports a workflow the person switched off by hand.

### Build it from gh and jq, with scanners as jobs

No maintained, general-purpose action builds a repository health issue from these signals. The nearest is github-community-projects/issue-metrics v5.0.3, which writes issue-response metrics into an issue ([issue-metrics](https://github.com/github-community-projects/issue-metrics)), and the 2026 "repo health" projects found by search have zero to four stars. greenrepo should therefore ship its own small collector script in the skill. The `ubuntu-slim` runner image already carries GitHub CLI 2.102.0 and jq 1.7 ([ubuntu-slim image](https://github.com/actions/runner-images/blob/main/images/ubuntu-slim/ubuntu-slim-Readme.md)), and zizmor's `superfluous-actions` audit flags single-purpose issue actions that duplicate `gh` ([zizmor audits](https://docs.zizmor.sh/audits/#superfluous-actions)). If an action is wanted, peter-evans/create-issue-from-file v6 runs on Node 24 and updates an issue by number ([create-issue-from-file](https://github.com/peter-evans/create-issue-from-file)); JasonEtco/create-an-issue last released in February 2024, declares Node 20 and matches by title ([create-an-issue](https://github.com/JasonEtco/create-an-issue)), and GitHub removed Node 20 from its runners on 2026-09-23 ([GitHub Changelog: Node 20 deprecation](https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/)).

Two of greenrepo's weekly duties, the external link check (DOC-05) and the dependency scan (DEP-04), fit as jobs of the health workflow itself, so there is one schedule to keep alive and one page to read. lycheeverse/lychee-action v2.9.0 takes `fail: false`, writes Markdown or JSON, exposes an exit code and supports a cache against rate limits ([lychee-action](https://github.com/lycheeverse/lychee-action)). google/osv-scanner-action v2.6.0's reusable workflow uploads SARIF to code scanning and fails on vulnerabilities by default ([OSV-Scanner action docs](https://google.github.io/osv-scanner/github-action/)); on a personal account's private repository, where code scanning does not exist, the job sets `upload-sarif: false` or calls the CLI with JSON output. On a public repository Dependabot alerts already cover most ecosystems, so OSV-Scanner matters mainly for ecosystems Dependabot does not watch. Scorecard is the exception and needs a workflow of its own: with `publish_results` its job may hold no env, use only five approved actions and run only on Ubuntu hosted runners, and the workflow may have no workflow-level write permissions ([scorecard-action](https://github.com/ossf/scorecard-action)). After Scorecard's services moved from Google Cloud to AWS in September 2026 and its BigQuery dataset was dropped, users must run scorecard-action v2.4.4 or later ([ossf/scorecard#5208](https://github.com/ossf/scorecard/issues/5208)). Its result artifact is kept five days, so Scorecard runs a few hours before the health workflow, or the collector reads `api.scorecard.dev` where results are published (herdsman returns 404 there today). Private repositories need GitHub Advanced Security for the action, which a personal account cannot buy; the Scorecard CLI is the documented fallback and is untested here.

### Costs round to zero; the hardening is the work

On public repositories, standard GitHub-hosted runners are free ([GitHub Docs: Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)), though no source confirmed in writing that the single-CPU `ubuntu-slim` runner counts as standard. Private repositories draw on **2,000 included minutes on Free and 3,000 on Pro** ([GitHub docs source: included quotas](https://github.com/github/docs/blob/main/data/reusables/billing/actions-included-quotas.md)), and the slim runner costs $0.002 a minute beyond that ([GitHub docs source: runner prices](https://github.com/github/docs/blob/main/data/reusables/billing/actions-standard-runner-prices.md)). Three jobs of one to three minutes, about 4.3 times a month, come to roughly 13–40 minutes, 1–2% of the Free quota; per-job rounding to whole minutes is likely but unverified, which favours fewer jobs on private repositories. Single-CPU runners stop jobs after 15 minutes ([GitHub Docs: single-CPU runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#single-cpu-runners)), so a large link check moves to `ubuntu-latest`. API limits are irrelevant at this scale: `GITHUB_TOKEN` gets **1,000 REST requests per hour per repository** ([GitHub Docs: REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)) and a run needs about 20–60, as long as the collector uses filtered list endpoints rather than the search API, which allows 30 requests a minute.

The hardening is greenrepo's existing CI rules applied without exception, plus two points specific to a job that reads outsiders' text. Triggers are `schedule` and `workflow_dispatch` only; the top level sets `permissions: {}`; the job that reads untrusted strings holds no write permission; every action is pinned by SHA with an exact version comment, which zizmor's `ref-version-mismatch` checks ([zizmor audits](https://docs.zizmor.sh/audits/#ref-version-mismatch)); and untrusted text reaches the issue through files and `--body-file`, never through `${{ }}` in `run:`, which `template-injection` flags ([zizmor audits](https://docs.zizmor.sh/audits/#template-injection)). The cron line avoids the top of the hour, because GitHub delays scheduled runs at high load "including the start of every hour" and may drop queued jobs, and schedules now accept an IANA `timezone` ([GitHub Docs: schedule event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)). A skeleton:

```yaml
name: health
on:
  schedule:
    - cron: "17 6 * * 1" # Mondays, off the hour
  workflow_dispatch:
permissions: {}
concurrency:
  group: health
  cancel-in-progress: false
jobs:
  collect: # reads untrusted text, writes nothing
    runs-on: ubuntu-slim
    timeout-minutes: 10
    permissions:
      contents: read # renewals file, expected settings, accepted list
      actions: read # workflow state, last scan conclusions
      issues: read # issues without an end state, last health body
      pull-requests: read # open dependency pull requests
      security-events: read # code scanning alerts, where they exist
      vulnerability-alerts: read # Dependabot alerts
    steps:
      - uses: actions/checkout@<sha> # vX.Y.Z
        with:
          persist-credentials: false
      - run: ./.github/health/collect.sh # gh and jq; writes report.md
        env:
          GH_TOKEN: ${{ github.token }}
      - uses: actions/upload-artifact@<sha> # vX.Y.Z
        with:
          name: health
          path: report.md
  publish: # one write: the health issue
    needs: collect
    runs-on: ubuntu-slim
    timeout-minutes: 5
    permissions:
      contents: read # the publish script
      issues: write # rewrite the issue; one comment per new critical item
    steps:
      - uses: actions/checkout@<sha> # vX.Y.Z
        with:
          persist-credentials: false
      - uses: actions/download-artifact@<sha> # vX.Y.Z
        with:
          name: health
      - run: ./.github/health/publish.sh report.md # edits only when changed
        env:
          GH_TOKEN: ${{ github.token }}
  keepalive: # runs even when collection fails
    needs: [collect, publish]
    if: always()
    runs-on: ubuntu-slim
    timeout-minutes: 2
    permissions:
      actions: write # re-enable this and inactivity-disabled schedules
    steps:
      - run: gh workflow enable health.yml --repo "$GITHUB_REPOSITORY"
        env:
          GH_TOKEN: ${{ github.token }}
```

The link-check and scanner jobs slot in beside `collect` with `contents: read` only. A privileged collection job, if a repository wants one at all, belongs in a protected environment so that zizmor's `secrets-outside-env` audit is satisfied ([zizmor audits](https://docs.zizmor.sh/audits/#secrets-outside-env)); the next section argues that most repositories should not want one.

## Settings drift needs a committed expected state, read with two credentials

A personal account gets repository rulesets (on public repositories with Free, on private ones with Pro) ([GitHub docs source: rulesets availability](https://github.com/github/docs/blob/HEAD/data/reusables/gated-features/repo-rules.md)), a **180-day ruleset history and JSON import and export**, with the bypass list left out of the export ([GitHub Docs: managing rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository)), per-repository Actions settings including the SHA-pinning policy and the default `GITHUB_TOKEN` permissions ([GitHub Docs: Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)), and account-wide "Enable all" and "enable by default for new repositories" switches for Dependabot alerts ([GitHub Docs: Dependabot alerts](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/configure-dependabot-alerts)). It does not get organisation rulesets, security configurations, which apply "to any repository within an organization" ([GitHub Docs: security configurations](https://docs.github.com/en/code-security/securing-your-organization/introduction-to-securing-your-organization-at-scale/about-enabling-security-features-at-scale)), or any account-level Actions policy. Nothing native stops the owner, the only admin, from editing a ruleset or switching off a security feature, and **nothing reports that it happened**. For a solo maintainer, drift comes from four places: the person's own clicks, GitHub changing defaults and adding settings, an upstream import in a fork, and a stolen owner credential. The first three are routine; only the last is urgent, and a thief with the owner's credential could also switch off the health workflow.

The tools for settings as code split cleanly between those that apply and those that detect, and none fits a personal account on both counts.

| Tool | Personal account | Catches drift | Runs as | Latest, 2026-10-10 |
| --- | --- | --- | --- | --- |
| safe-settings | organisation model | yes, reverts it | self-hosted app | 3.0.0 |
| Probot settings app | yes, hosted free | no, applies on edit | hosted app | v5.0.14 |
| Terraform provider | yes, with `owner` | on each `plan` | CLI and state | v6.13.0 |
| github-settings-as-code | yes, with a PAT | `mode: check` | Action | v2.0.0, 3 stars |
| Allstar | unconfirmed | issue per policy | own App, Action | v4.6, unhosted |
| Minder | yes, enrols users | alert or fix | hosted, free if public | v0.3.2 |

safe-settings is the strongest at holding settings, syncing on a schedule and reverting changes made in the UI, but it calls itself "Policy-as-Code for GitHub Organizations" and keeps settings in an organisation's `admin` repository ([safe-settings](https://github.com/github-community-projects/safe-settings)). The Probot settings app has a free hosted version that installs on personal repositories, but it applies `.github/settings.yml` only when that file changes on the default branch ([settings app index.js](https://github.com/repository-settings/app/blob/HEAD/index.js)), so a change made in the UI survives until the next edit of the file, and its README warns that it "inherently escalates anyone with `push` permissions to the admin role" ([repository-settings/app](https://github.com/repository-settings/app)). Terraform's provider works with a personal owner and token but detects drift only when someone runs `plan`, with state stored somewhere ([terraform-provider-github](https://github.com/integrations/terraform-provider-github)). Vivswan/github-settings-as-code is the closest fit, an Action with a `mode: check` drift report, but it was created in July 2026, needs an admin-scoped PAT because "the default `GITHUB_TOKEN` is not enough", and has one maintainer ([github-settings-as-code](https://github.com/Vivswan/github-settings-as-code)). Allstar shows the risk of depending on hosted services: OpenSSF retired its hosted app in August 2026 "due to funding constraints" ([ossf/allstar#881](https://github.com/ossf/allstar/issues/881)), self-hosting needs a GitHub App and a `.allstar` repository, and its branch-protection policy reads only classic branch protection, with a request to read rulesets open since 2023 ([ossf/allstar#475](https://github.com/ossf/allstar/issues/475)), so it would misreport greenrepo's ruleset-based repositories. Minder can enrol a personal account and its hosted instance is free for public repositories, but it is pre-1.0 and grants a third party standing access ([mindersec/minder](https://github.com/mindersec/minder)).

greenrepo should therefore build drift detection into what it already has and keep it **report-only**. Each repository commits its expected settings: the ruleset exports exactly as GitHub produces them, and a small file of the other settings in GitHub's API field names (`allow_squash_merge`, `delete_branch_on_merge`, the `security_and_analysis` switches, `default_workflow_permissions`, `can_approve_pull_request_reviews`). One diff script then runs with two credentials. Weekly in CI, `GITHUB_TOKEN` diffs everything it can read: the rulesets, which are the most important settings of all, private vulnerability reporting and the state of every workflow. Monthly, the person's own agent session runs the same script with the person's `gh` login and diffs what only an admin can read: security switches, the Actions policy and default token, merge settings, deploy keys and secret ages, and on public repositories the secret scanning alerts. The person's ordinary `gh` login, with the classic `repo` scope, read herdsman's secret scanning alerts, deploy keys, secret dates and security block on 2026-10-10 ([herdsman](https://github.com/remziduzagac/herdsman)). That split stores **no admin-read secret anywhere**, keeps the sensitive results out of a public issue, and accepts a month of latency on settings that only the owner can change. Applying settings stays a person's act, because writing them needs admin credentials, which Terraform's documentation and github-settings-as-code both confirm, and uv's own threat model rates "a scheduled workflow [that] automatically runs mutable third-party code with repository-write, publishing, or equivalent credentials" as High severity ([uv repository threat model](https://github.com/astral-sh/uv/blob/main/agents/references/repository-threat-model.md)).

Two variants suit specific cases. A private repository that wants weekly admin checks can add the privileged job with a read-only fine-grained token (Administration, Secrets and Secret scanning alerts, all read) in an environment, which SET-08 already allows. A maintainer with many repositories can instead run the privileged diff from one private control repository with one read-only token across all of them, trading SET-08's one-repository rule for one credential to renew instead of many; that is a deliberate exception and should be written as one. The ruleset export omits bypass actors, so they stay a twice-yearly manual check, and every schema lags new GitHub settings, so the twice-yearly review also compares the expected-settings file with GitHub's current options. For that review, the OpenSSF's OSPS Baseline scanner, v0.32.0 of 2026-10-09, is the only maintained tool found that assesses repository settings against a published control catalogue ([pvtr-github-repo-scanner](https://github.com/ossf/pvtr-github-repo-scanner)) and is worth reading before writing greenrepo's own checks. Repolinter, the old file-tree linter, was archived on 2026-02-06 ([todogroup/repolinter](https://github.com/todogroup/repolinter)). herdsman is the obvious first case: its MAINTAINING.md records its two rulesets and its security choices as prose, which an expected-settings file would turn into something a script can diff.

## Agents should start in the person's session and earn their way into CI

### Deterministic bots already do the detecting, almost free

Dependabot is built in and MIT-licensed; Renovate adds a dashboard by default, wider platform support and shared presets under the AGPL ([Renovate bot comparison](https://docs.renovatebot.com/bot-comparison/)), and its Mend-hosted Community Cloud is free for personal accounts and private repositories ([Renovate: Mend-hosted](https://docs.renovatebot.com/mend-hosted/overview/)). Since 2026-07-14 Dependabot version updates wait three days after a release by default, while security updates still open at once ([GitHub Changelog](https://github.blog/changelog/2026-07-14-dependabot-version-updates-introduce-default-package-cooldown/)). herdr's configuration, monthly, everything grouped, at most one open pull request per ecosystem, is a good low-noise template, and where Renovate runs, the health issue links to its dashboard rather than copying its lists. release-please (v17.11.2) and release-drafter (v7.10.0) fit greenrepo's principle exactly, because they open release pull requests or drafts that the person merges or publishes ([release-please](https://github.com/googleapis/release-please); [release-drafter](https://github.com/release-drafter/release-drafter)). Mergify is free for open source ([Mergify pricing](https://mergify.com/pricing)), but merge queues serve teams more than one person.

Stale handling is where defaults hurt. actions/stale v11 marks issues stale after 60 days and **closes them seven days later unless told otherwise** ([actions/stale](https://github.com/actions/stale)). cli/cli marks issues stale after 30 days and never closes them (`days_before_close: -1`), with a `keep` label and a separate job for issues waiting on the reporter ([cli/cli triage-scheduled-tasks.yml](https://github.com/cli/cli/blob/trunk/.github/workflows/triage-scheduled-tasks.yml)). Jacob Tomlinson's rule draws the line: automate closing only "when responsibility rests on the user/contributor, never when it rests on maintainers" ([Jacob Tomlinson](https://jacobtomlinson.dev/posts/2024/most-stale-bots-are-anti-user-and-anti-contributor-but-they-dont-have-to-be/)), and a study of 20 large projects found a considerable drop in active contributors after stale bots were adopted ([Khatoonabadi et al.](https://arxiv.org/abs/2305.18150)). greenrepo's UPK-07 already says this; its how-to should add that the stale action is configured with `only-labels` set to the needs-info label and an explicit close timer, because its defaults do the opposite.

### Seven agent options, and only some leave the decision with the person

| Option | Started by | Writes as | Paid from | Fit for greenrepo |
| --- | --- | --- | --- | --- |
| Local session with a skill | the person | the person, after confirming | subscription | the default |
| Desktop task or `/loop` | a local timer | the person, per permission mode | subscription | read-only drafts |
| `claude-code-action` | schedule, dispatch | job token or own App | subscription or API | optional CI pass |
| `codex-action` | schedule, dispatch | job token | API key | optional CI pass |
| Copilot Automations | timer, issue, PR | the creator | AI Credits | narrow tools only |
| Claude Code Routines | timer, API, events | the person, no prompts | subscription | narrow tools only |
| GitHub Agentic Workflows | any event | safe-output jobs | minutes and engine | watch list |

GitHub's Copilot cloud agent keeps the human checkpoint by design: only users with write access can start it, workflows on its pull requests wait for approval, and it "cannot approve or merge a pull request" ([GitHub Docs: cloud agent risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Its Automations, generally available since 2026-06-02, run hourly, daily or weekly or on new issues and pull requests, with a chosen set of tools, but they run under the identity of the user who created them, bill that user, and at launch supported private and internal repositories with public ones "coming soon" ([GitHub Changelog](https://github.blog/changelog/2026-06-02-schedule-and-automate-tasks-with-copilot-cloud-agent/)). Claude Code Routines are similar on Anthropic's side: they run "autonomously ... without stopping for approval", everything they do "appears as you", and every connector is included unless removed ([Claude Code docs: routines](https://code.claude.com/docs/en/routines)). An agent that labels and comments as the person makes its writes indistinguishable from the person's decisions, so both fit greenrepo only with their tools narrowed to things that are not public.

GitHub Agentic Workflows has the strongest architecture on paper: a read-only agent job, writes deferred to separate safe-output jobs, a second agent that screens outputs, a firewall with a domain allowlist, and on public repositories content only from owners, members and collaborators ([gh-aw architecture](https://github.github.com/gh-aw/introduction/architecture/)). It is also **pre-release in every version (v0.91.7 on 2026-10-09)**, its README warns "Use it with caution, and at your own risk", and its August and September 2026 advisories include critical ones, among them safe-output artifacts that could expose CI trigger tokens and arbitrary host and Docker-socket mounts through MCP server configuration ([github/gh-aw](https://github.com/github/gh-aw)). It belongs on greenrepo's watch list, not in its baseline. `claude-code-action` (v1.0.248) runs on a schedule with a prompt and has "no shell or GitHub API access until you grant the tools"; scheduled runs skip the write-access check, bot actors are rejected unless listed in `allowed_bots`, and authentication can use a subscription token from `claude setup-token`, an API key or OIDC federation, which avoids a long-lived secret ([Claude Code docs: GitHub Actions](https://code.claude.com/docs/en/github-actions)). By default it pushes a branch and leaves opening the pull request to the person ([claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)). `openai/codex-action` offers a `read-only` sandbox and a `drop-sudo` safety strategy, and its docs advise limiting "who can start the workflow" ([Codex docs: GitHub Action](https://learn.chatgpt.com/docs/github-action)). For pull request review, CodeRabbit is free on public repositories ([CodeRabbit pricing](https://www.coderabbit.ai/pricing)), while Anthropic's managed Code Review is for Team and Enterprise plans at $15–25 a review ([Claude Code docs: code review](https://code.claude.com/docs/en/code-review)); `/code-review` run locally costs nothing beyond the subscription.

### Prompt injection decides where agents run

The deciding risk is not cost but text. In "PromptPwnd", an issue told the Gemini CLI agent in Google's own repository to put `$GEMINI_API_KEY` and `$GITHUB_TOKEN` into an issue body, and it did; Claude Code, Codex and GitHub AI Inference actions were affected by the same pattern ([Aikido](https://www.aikido.dev/blog/promptpwnd-github-actions-ai-agents)). "Comment and Control", presented at Black Hat on 2026-08-05, made agents expose secrets through a malicious issue or pull request comment, with **CVE-2026-54316 assigned to Claude Code and CVE-2026-12537, rated CVSS 10.0, to Gemini CLI** ([Cloud Security Alliance note](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-coding-agent-ci-prompt-injection-202608/)). In a January 2026 chain against claude-code-action, an issue opened by a malicious GitHub App passed the permission check because its actor name ended in `[bot]`, and the injected prompt read `/proc/self/environ` for OIDC request tokens ([Cloud Security Alliance note](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-github-action-prompt-injection/)). Both notes are secondary write-ups. claude-code-action strips hidden content from its inputs "but new bypass techniques may emerge", and its documentation is blunt about credentials: "Do not use a personal access token — a static token does not rotate between runs and could be partially or fully recovered over time via prompt injection" ([claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)).

The projects that run upkeep agents converge on one contract. uv's triage agent runs under a Codex profile that extends `:read-only`, may write only to the temp directory and reach only `api.github.com` and `github.com` ([uv Codex config](https://github.com/astral-sh/uv/blob/main/agents/codex/config.toml)); it returns JSON against a schema, and its `draft_response` "is a draft for maintainer review only; do not post it" ([uv triage prompt](https://github.com/astral-sh/uv/blob/main/agents/prompts/triage-issue.md)); writes happen in separate jobs with short-lived tokens. cli/cli's triage agent may suggest at most three labels, each marked as a suggestion "requiring maintainer approval", and post one comment; the only label it applies itself is `suspected-spam`, under the instruction "Be conservative. A false positive closes a real user's issue" ([cli/cli issue-triage.md](https://github.com/cli/cli/blob/trunk/.github/workflows/issue-triage.md)). deno's triage skill runs by hand and says "Always confirm with the user before posting comments or modifying labels on GitHub" ([deno issue-triage skill](https://github.com/denoland/deno/blob/main/.claude/skills/issue-triage/SKILL.md)), and herdr's triage skill only reads and recommends ([herdr triage skill](https://github.com/herdrdev/herdr/blob/master/.agents/skills/triage/SKILL.md)). Agents classify, deduplicate, reproduce and draft; people close, merge and release.

GitHub added platform gates that help. Since 2026-06-11, pull requests opened by `github-actions[bot]` run workflows only after a user with write access approves ([GitHub Changelog](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/)); users report that a PAT or App token avoids the approval ([community discussion 199292](https://github.com/orgs/community/discussions/199292)), which removes a checkpoint the standard wants and should be a written choice, not a workaround. Since 2026-07-28 GitHub holds potentially malicious runs on public repositories for a collaborator's approval ([GitHub Changelog](https://github.blog/changelog/2026-07-28-github-actions-holds-potentially-malicious-workflows-for-approval/)), and from 2026-11-02 workflow execution protections disable `pull_request_target` on public repositories without an event policy allowing it ([GitHub Changelog](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/)); neither announcement says whether the protections cover personal-account repositories.

### Run upkeep agents by hand first, on a timer second, in CI last

| Aspect | Local, started by the person | CI on a schedule |
| --- | --- | --- |
| Human checkpoint | built in: the person is present | must be built: drafts, suggestions |
| Credentials | the person's `gh` login, broad | a job-scoped token, narrow |
| Secrets stored in the repository | none | an API key or subscription token |
| Untrusted text | read with the person watching | read unattended |
| Runs while the person is away | no | yes |
| Audit trail | the session transcript | Actions logs and artifacts |

The default order follows from the table. First, a local session in the greenrepo skill's keep mode, started by the person, reads the health issue body, raises what is red, proposes fixes as branches and draft pull requests, and posts labels or comments only after the person confirms, as deno's skill does. Second, if the person wants work waiting for them, a Desktop scheduled task or `/loop` runs the same skill read-only and leaves a draft; Desktop tasks run only while the app is open and the machine awake, catch up one missed run within seven days, and in Manual mode stall until approved ([Claude Code docs: Desktop scheduled tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks)). Third, and only for a repository that needs it, a CI pass. A local session is not automatically safer: it trades a narrow job token for the owner's broad login, protected only by the person's attention. Keep-mode sessions therefore restrict their allowed tools to read commands and named write verbs, as deno's skill limits its shell commands to `gh`, `deno` and `git`, and never run upkeep in a mode that skips permission prompts.

A CI pass is affordable when it is gated. cli/cli found that a run with nothing to do still made eight model calls costing "~50-75 AIC", and added a deterministic pre-flight step so that "a no-work run charges zero AI Credits" ([cli/cli dependabot-triage.md](https://github.com/cli/cli/blob/trunk/.github/workflows/dependabot-triage.md)); at $0.01 a credit ([GitHub blog: usage-based billing](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)), that is fifty to seventy-five cents for every run that finds nothing to do. With `claude-code-action`, a subscription token adds no marginal API cost and Actions minutes are free on public repositories, so the real price of a scheduled agent is a stored long-lived credential and an unattended reader of untrusted text. No source in this research measured the token cost of a typical Claude upkeep pass.

## Twelve rule edits make greenrepo's upkeep enforceable

The draft's upkeep part has the right principle and the right calendar; what it lacks is the mechanics that keep the health issue quiet, the line between what CI and the person's session read, a place for settings drift, and limits for agents that act as the person. The table gives the proposed rule rows; the paragraphs after it give the reasons and the how-to text that changes.

| ID | Proposed rule | Scope |
| --- | --- | --- |
| UPK-03 | Schedules kept alive by the health workflow; credentials and renewals in a file it reads | Core |
| UPK-04 | A weekly health workflow rewrites one labelled health issue, only when its content changes | Core |
| UPK-05 | Upkeep duties written down: where agents run, what they check, propose, and do alone | Core |
| UPK-09 | Delivery renewals (domains, certificates, accounts, store deadlines) in the renewals file | Delivery |
| UPK-13 | A scheduled agent pass behind a no-op gate: a read-only agent job and one narrow write job | Opt |
| UPK-15 | Expected settings committed; drift reported weekly and monthly, never applied by automation | Core |
| UPK-16 | Accepted deviations listed with a reason and a review date, shown apart in the health issue | Core |
| CI-13 | The health workflow: schedule and dispatch only, read jobs apart from its one write job | Core |
| CI-14 | Agent workflows: trusted triggers, job-scoped tokens, a tool allowlist, an explicit bot list | Core |
| AGT-04 | No vulnerability details in public, the health issue included | Shared |
| AGT-10 | Third-party text is data: issues, comments, PR titles, changelogs, logs, the health issue | Core |
| SET-08 | Tokens fine-grained, one repository, expiring; deploy keys rotated by date; all listed | Core |

**UPK-04** drops "pinned" and "every signal" from the rule. Its how-to names the signals in the table of the second section; finds the issue by the `repository-health` label and a body marker; writes only when the text changed; opens with the last run's date and link; orders sections by who acts (the person, an agent, accepted, not available); caps lists and links to evidence; shows counts only for Dependabot alerts on public repositories and never shows secret scanning alerts there; adds one comment when a critical item first appears; reopens the issue if it is closed; and says to pin it only when a slot is free and to lock its conversation. Per-problem events, such as a flaky test under QA-09 or a failed release, get their own issues, which the health issue links. **UPK-16** is new and gives that page its accepted section: one file of deviations, each with a reason and a review date, read by both the health workflow and the audit's "not applicable" list, so Scorecard's Code-Review and Contributors and herdsman's disabled security updates are decided once instead of showing red every week.

**UPK-03** and **CI-13** replace the monthly manual check of schedules with machinery: the health workflow re-enables itself on every run in a job that runs even when collection fails, re-enables schedules GitHub switched off for inactivity, and reports those the person switched off by hand; and each agent session treats a last run older than eight days as red. CI-13 loses "upkeep confirms it is still enabled" and gains the job split shown in the skeleton, with Scorecard in its own workflow on public repositories. The credential half of UPK-03, together with **SET-08** and **UPK-09**, moves the list of tokens, keys and renewals out of prose in the maintaining procedures into one renewals file the workflow reads, because GitHub exposes no expiry for deploy keys or for a personal account's tokens. SET-08 also changes "expiring" for deploy keys, which cannot expire, to a rotation date in that file with their `last_used` date checked in the monthly session.

**UPK-15** is new: each repository commits its ruleset exports and a settings file in API field names; CI diffs the parts `GITHUB_TOKEN` can read every week; the keep-mode session diffs the admin-only parts monthly with the person's login; automation never applies settings. Its how-to names the two exceptions from the previous section, a privileged job for private repositories and a private control repository for many, each written down as a deliberate choice. The twice-yearly review in UPK-02 adds the expected-settings file, the accepted list, bypass actors and the renewals file to what it reviews.

**UPK-05** fixes a contradiction in the draft. Its list of what agents do alone includes "label, comment", while the same sentence leaves "anything public" to the person, and labels and comments on a shared repository are public and reach other people. The edited duties say that agents may read, run checks, push branches and open draft pull requests alone; that labels and comments addressed to other people are proposals until the person approves them, following cli/cli's suggestions and deno's confirmation rule; and where agents run: by default in a session the person starts, scheduled local runs read-only, and cloud agents that act as the person (Copilot Automations, Routines) only with tools that cannot write publicly. **UPK-13** keeps its optional scope and gains the CI contract: a deterministic gate that skips the model when nothing changed, a read-only agent job with schema-checked output, one write job limited to a proposals section of the health issue, label suggestions and draft pull requests, `timeout-minutes` with a turn limit, no PAT, and GitHub Agentic Workflows left out until it ships stable releases. Its how-to drops "it costs money per run", which a gate and a subscription token make nearly false, and states the real cost: a stored credential and an unattended reader of outsiders' text.

**CI-14** moves from Shared to Core, applying whenever a repository has an agent workflow, because even a private solo repository feeds agents third-party text through dependency pull requests and their changelogs, which cli/cli calls attacker-influenceable ([cli/cli dependabot-triage.md](https://github.com/cli/cli/blob/trunk/.github/workflows/dependabot-triage.md)). It adds job-scoped tokens or OIDC instead of PATs, an explicit `allowed_bots` list instead of a wildcard after the `[bot]`-actor chain, and a tool allowlist. **AGT-04** splits for the same reason: the vulnerability-disclosure half stays Shared and now names the health issue explicitly, while the untrusted-text half becomes **AGT-10**, Core, covering the health issue's quoted strings as well as issues, comments, pull request titles, changelogs and logs.

Three edits sit outside the rule table. The calendar's monthly row becomes "merge the grouped dependency pull requests; run the admin-only settings diff and read secret scanning alerts in a keep-mode session", its each-session row adds "flag the health issue if its last run is over eight days old", and its twice-yearly row adds the expected-settings file, the accepted list, the renewals file and deploy-key rotation. The section "When the platform does not offer a feature" needs two corrections from this research: code scanning on a personal account's private repositories cannot be bought at all, since GitHub Code Security is sold for organisation-owned repositories, and secret scanning on user-owned private repositories exists only on Enterprise Cloud with managed users or on Enterprise Server, so the health issue reports both as "not available" rather than as zero alerts. Finally, the open questions should list what must be tested before the skill ships: whether `vulnerability-alerts: read` works on a personal-account repository, whether `GITHUB_TOKEN` may pin an issue, whether the bot's issue edits count as repository activity, whether `ubuntu-slim` is free on public repositories, and whether workflow execution protections and Copilot Automations reach personal-account public repositories. A first `workflow_dispatch` run of the collector on herdsman, which has no scheduled workflow today, answers most of them in an afternoon.

## Conclusion

The September 2026 permission change drew a line that greenrepo can follow rather than fight. What `GITHUB_TOKEN` can now read is, almost exactly, what may appear on a public page, and what it still cannot read (secret scanning alerts, security switches, merge settings, deploy keys) is what should never appear there. The boundary between CI and the person's own session is therefore also the boundary between public and private information, and a design that puts admin-level reads in the monthly keep-mode session gains on three counts at once: no stored admin secret, no sensitive line in a public issue, and no new credential to renew. The draft treated the health issue as a report and the scheduled agent as a cost question; the evidence says the issue is a piece of state that must stay quiet to stay read, and the agent is an identity and injection question whose cost a ten-line gate removes.

The ground is still moving, and the standard's dates matter more here than anywhere else in it. In the last quarter alone, OpenSSF's hosted Allstar app disappeared, Scorecard changed infrastructure and forced an upgrade, Node 20 left the runners, GitHub Agentic Workflows shipped critical fixes, and `pull_request_target` loses its default on 2026-11-02. A health workflow built on `gh`, `jq` and documented endpoints, with its assumptions tested on herdsman first, will survive those shifts better than any hosted service or young action, and the twice-yearly review should re-test precisely the six assumptions this research could not confirm.
