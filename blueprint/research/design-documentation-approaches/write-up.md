# Keep the blueprint's skeleton, cut its ceremony

The blueprint proposal already has the shape that the longest-lived design processes ended up with, so refining it is mostly a matter of subtraction. Python's PEPs, Rust's RFCs after RFC 1636, and OpenSpec all keep change proposals as frozen history and one separate tree as the current truth, which is the blueprint's `prd/` to `design/` merge; the decision format (short entries, global IDs, status read from "Superseded by" notes) is a leaner Nygard or MADR record with adr-tools' link convention. The evidence warns against volume and ceremony, not against too little structure: one practitioner's Spec Kit trial produced **2,577 lines of markdown for 689 lines of code**, BMAD and Agent OS spent 2025–2026 deleting personas, sharding, per-task reports and spec phases, and an ETH Zurich study found that context files raise agent cost by **over 20%** without generally improving task success. Three cheap additions close the real gaps: make `implemented` a gate (reconcile with what shipped, merge the delta, add a "historical, see `design/…`" banner), give design files stable headings so deltas merge mechanically, and make every decision name its cost. Four subtractions keep it simple: tasks as a checklist inside the PRD until one needs its own file, five PRD statuses instead of six, front matter limited to facts that have no other home, and no git-derived dates in committed indexes. The tooling should stay one Python script of roughly 200 lines, run by a git hook and by CI, because no ADR or spec-driven tool fits themed files of decision entries and the best-known ADR CLI has had no release since 2018.

## Mature processes freeze proposals and keep one current truth

The main question for any proposal process is what happens to the proposal after the change ships. Mature projects answer it in one of two ways. PEP 1 says that once resolved, a PEP "is considered a historical document rather than a living specification", with formal documentation "maintained elsewhere, such as the Language Reference" ([PEP 1](https://peps.python.org/pep-0001/)). PEP 12 then adds a `canonical-doc` banner that renders "This PEP is a historical document. The up-to-date, canonical documentation can now be found at [link]" ([PEP 12](https://peps.python.org/pep-0012/)). Rust learned the same lesson the hard way. RFC 1636 found that new features were "often documented *only* in the RFCs which propose them", and it made reference documentation a gate: "Stabilization of a feature must not proceed until" the RFC's teaching requirements are fulfilled ([RFC 1636](https://rust-lang.github.io/rfcs/1636-document_all_features.html)). Six years later a former core team member still complained that "it is impossible to tell from reading an accepted RFC whether it was implemented or stabilised, and if it was, whether the implementation matched the RFC" ([Cameron](https://www.ncameron.org/blog/the-problem-with-rfcs/)).

Oxide takes the other path. A `committed` RFD is "an explanation of how a system works", so the proposal itself becomes the living design ([RFD 1](https://rfd.shared.oxide.computer/rfd/0001)). The cost is that the current design is spread across many RFDs. At scale, Oxide needed a CSV index, short URLs, a chat bot and a full-text search site to keep them findable ([RFD 1](https://rfd.shared.oxide.computer/rfd/0001); [Oxide](https://oxide.computer/blog/a-tool-for-discussion)). Kubernetes KEPs sit in between. Each is a folder per enhancement that is updated across releases until `implemented`, meaning "no longer actively changed" ([KEP-0000](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md)).

The agent-era tools rediscovered the split. OpenSpec keeps `openspec/specs/` as "the source of truth" and puts proposals in `openspec/changes/<name>/`. The archive step merges each change's `ADDED`, `MODIFIED` and `REMOVED` requirements into the main specs and moves the folder to `changes/archive/YYYY-MM-DD-<name>/` ([OpenSpec concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md); [CLI](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md)). Its one rule about drift is the one that matters: "before you archive, make the specs honest about what the code does" ([OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/editing-changes.md)). GitHub's Spec Kit has no system-wide spec at all. It describes three persistence models (flow-back, flow-forward and living spec), says "None is the default, and none is required", and admits that flow-forward leaves context duplicated and fragmented ([Spec Kit](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md)). Birgitta Böckeler classed both Spec Kit and Kiro as "spec-first": Kiro has "no spec-anchoring strategy" ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

| Process | Unit | After the change ships |
| --- | --- | --- |
| PEP | one file per PEP | frozen history; banner points to the reference |
| Rust RFC | `text/NNNN-name.md` | frozen; a Reference update gates stabilisation |
| Oxide RFD | `rfd/NNNN/README.adoc` | `committed`; the RFD itself describes the system |
| KEP | `keps/sig-x/NNNN-name/` plus `kep.yaml` | `implemented`, no longer actively changed |
| OpenSpec | `changes/<name>/` with deltas | deltas merged into `specs/`, folder archived by date |
| Spec Kit | `specs/NNN-feature/` | the team chooses; no system-wide spec exists |
| Blueprint | `prd/NNNN-slug/` | delta merged into `design/`, PRD kept as history |

The blueprint is therefore the PEP and OpenSpec model with a KEP-style folder, which is the best-supported variant for anyone who wants one answer to "how does it work now". Its weakness is the same one Rust had: the merge is a promise unless something enforces it. Status vocabularies point the same way. KEPs run provisional, implementable, implemented, plus deferred, rejected, withdrawn and replaced, and have **no in-progress state** ([KEP-0000](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md)). Swift's Accepted covers proposals "either awaiting implementation or … actively being implemented" ([Swift Evolution](https://github.com/swiftlang/swift-evolution/blob/main/process.md)). PEP separates Withdrawn from Rejected only because the author and the decider are different people ([PEP 1](https://peps.python.org/pep-0001/)). Ember's post-acceptance stages are worth noting because one of them is a documentation gate: a feature reaches "Recommended" only once it "is integrated into the tutorial and the guides prose" ([Ember RFCs](https://github.com/emberjs/rfcs/blob/main/README.md)).

The content advice converges on short documents and on skipping them when a change is obvious. Google-style design docs centre on context and scope, goals and non-goals, the design and its trade-offs, and alternatives considered. They recommend 1–3-page "mini design docs" for incremental work and warn against copying interface definitions or schemas that "quickly get out of date" ([Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/)). Shape Up's pitch adds an **Appetite** (how much time the change deserves) and **No-gos**, and it rejects backlogs because "the time spent constantly reviewing, grooming and organizing old ideas prevents everyone from moving forward" ([Shape Up ch. 6](https://basecamp.com/shapeup/1.5-chapter-06); [ch. 7](https://basecamp.com/shapeup/2.1-chapter-07)). The thresholds for when to write one agree across sources: HashiCorp says "If implementing your idea will take less time than writing it up, you can probably go ahead without an RFC" ([HashiCorp](https://www.hashicorp.com/en/how-hashicorp-works/articles/writing-practices-and-culture)), and Anthropic says "If you could describe the diff in one sentence, skip the plan" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The same Anthropic page sets out what a useful spec contains: "they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step". Rust's fixed nine-section template is the warning on the other side: "one rigid template … for all RFCs, independent of the domain or the magnitude of the change" ([Cameron](https://www.ncameron.org/blog/the-problem-with-rfcs/)).

## Decision records fail by growing too long or leaving out the cost

The proposed entry (Decision, Why, optional Not chosen) is Nygard's record without a Status section, plus MADR's considered options. Nygard's 2011 format has five sections, "one or two pages", and keeps a reversed decision marked superseded rather than deleted, on the argument that "large documents are never kept up to date" ([Nygard](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)). The minimal template of MADR 4.0.0 (September 2024) needs only a title, the context and problem, the considered options and the outcome ("Chosen option: … because …"). All of its front matter is optional, and since 4.0 the status holds only an identifier, such as "superseded by ADR-0123", not a link ([MADR](https://github.com/adr/madr); [changelog](https://github.com/adr/madr/blob/develop/CHANGELOG.md)). The closest established match to a one-paragraph entry is Zimmermann's Y-statement: "In the context of …, facing …, we decided for … and neglected …, to achieve …, **accepting that** …" ([Zimmermann](https://www.ozimmer.ch/practices/2020/04/27/ArchitectureDecisionMaking.html)). The blueprint format covers every clause of that sentence except the last one, the accepted cost.

That missing clause is the gap critics flag most often. Zimmermann's 2026 list of ADR mistakes includes missing alternatives ("A decision that does not identify alternatives and chooses one of them is not a decision"), unexplained rejections, no negative consequences ("there are no free design lunches"), and "Unvetted AI-Generated Content" ([Zimmermann 2026](https://ozimmer.ch/practices/2026/09/12/ADRMistakes.html)). His older anti-pattern catalogue adds the **Mega-ADR** and the **Blueprint/Policy in disguise**, a record written in a cookbook tone rather than as a journal entry ([Zimmermann 2023](https://ozimmer.ch/practices/2023/04/03/ADRCreation.html)). bool.dev warns against "Combining multiple decisions into one ADR" and against using records as developer documentation ([bool.dev](https://bool.dev/blog/detail/10-adr-antipatterns)). With about 200 entries written in one week of trailscout design work, the realistic risk is not too few records but entries that slide into specification. Detail belongs in `design/`, which the decision links to.

Grouping many entries per themed file has **no authoritative precedent**. Every mainstream format and tool (adr-tools, log4brains, MADR) assumes one file per decision. Microsoft's playbook keeps a `decision-log.md` table, but only as a summary of separate ADRs ([Microsoft](https://microsoft.github.io/code-with-engineering-playbook/design/design-reviews/decision-log/)). Spotify's answer to "When should I write an Architecture Decision Record?" is "Almost always!", with lightweight records for small choices ([Spotify](https://engineering.atspotify.com/2020/04/when-should-i-write-an-architecture-decision-record)). Themed files are still defensible because the global ID, not the file, is the record's identity, much like log4brains' global and package scopes ([log4brains](https://github.com/thomvaill/log4brains)). The consequence is that entries must be cited only by ID. A GitHub heading slug for `## D201: The layers of the interfaces (2026-10-07)` contains the whole title, so retitling an entry breaks every anchor link to it ([markdownlint MD051](https://github.com/DavidAnson/markdownlint/blob/main/doc/md051.md)). Plain `(D201)` resolved by a validator survives retitling and re-theming.

On superseding, the sources agree that records should be immutable apart from status. Fowler: "Once an ADR is accepted, it should never be reopened or changed - instead it should be superseded" ([Fowler](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html)). AWS proposes a new ADR that supersedes the old one ([AWS](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)). The blueprint's relationship notes at the top of an entry match adr-tools exactly. Its `adr link` command writes pairs such as "Amends / Amended by" and "Clarifies / Clarified by" into the Status section of both records ([adr-tools tests](https://github.com/npryce/adr-tools/blob/master/tests/linking.expected)). "Detailed by" has no standard precedent, but adr-tools' free-form pairs show the pattern is accepted. Deriving status from those notes, with no separate field, is sound. For agents, a 2026 guide recommends exactly that: a visible "Superseded by" status with reciprocal links, an index table for scanning, and a CLAUDE.md pointer instead of loading the whole directory, which "burns context and makes unrelated decisions compete for attention" ([dev.to](https://dev.to/naman_here/adrs-for-ai-coding-agents-how-to-make-every-agent-read-architecture-decisions-3he4)). With 200 or more entries, the agent-specific danger is a forgotten back-link that leaves two live, contradictory rules. A reciprocity check in the validator is the cheapest guard.

The tools are not worth adopting. adr-tools' last release, 3.0.0, dates from July 2018 ([adr-tools](https://github.com/npryce/adr-tools)), and log4brains has been quiet since its December 2024 release ([log4brains](https://github.com/thomvaill/log4brains)). What they automate (the next number, reciprocal links and an index) is about thirty lines of script once entries have a predictable heading shape. Negative decisions repay the effort most. In one Cline user's report, recording that a UI column had been removed stopped the agent re-adding it while fixing tests ([kangax](https://kangax.substack.com/p/memory-bank-and-the-many-failures)). That is exactly the kind of fact an agent cannot infer from code.

## Spec toolkits spent 2025–2026 deleting their own structure

Spec Kit is the heaviest and most popular toolkit, at v1.1.1 and about 140,000 stars in October 2026 ([releases](https://github.com/github/spec-kit/releases)). It shows where volume leads. Each feature gets `specs/NNN-feature/` with a spec, a plan, research, a data model, a quickstart, contracts and tasks, behind a "Constitution Check" gate ([plan template](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)). Colin Eberhardt measured one increment: **33.5 minutes of agent time, 689 lines of code, 2,577 lines of markdown and 3.5 hours of review**. Built iteratively without Spec Kit, the same work took 8 minutes of agent time and 24 minutes of review, and an obvious bug still slipped through the spec-driven run ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)). François Zaninotto saw a simple date-display feature produce "8 files and 1,300 lines of text" ([Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)). Böckeler watched Kiro turn a small bug into four user stories with sixteen acceptance criteria, concluded "I'd rather review code than all these markdown files", and saw agents ignore the notes anyway ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Thoughtworks keeps spec-driven development in **Assess** and warns that practitioners "may be relearning a bitter lesson—that handcrafting detailed rules for AI ultimately doesn't scale" ([Thoughtworks Radar](https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development)).

The frameworks' own changelogs are the strongest evidence, because they record authors removing what they had built. BMAD v6.11.0 (August 2026) cut core skills "from fourteen skills to eight" and retired document sharding "with no replacement". It replaced generated project overviews with "just one verified block in `AGENTS.md`", and the release "deletes about 1,900 more lines than it adds". It also moved sprint status into a tested script with a "Fix sprint status" action that "rebuilds a broken or drifted file", which shows that agent-maintained status files do drift ([BMAD changelog](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)). BMAD's docs now say "You need a PRD when more than one person must agree on what the product is, or more than one epic must not diverge; otherwise skip it" ([BMAD](https://docs.bmad-method.org/plan/choose-a-planning-path/)). Agent OS removed its roles system two weeks after adding it, as "Too complex", along with "verification documentation bloat". In v3 it dropped spec writing and task orchestration because "frontier models handle this well on their own now" ([Agent OS changelog](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)). Task Master deprecated generating per-task files in 0.34.0 and keeps everything in one `tasks.json` ([Task Master changelog](https://github.com/eyaltoledano/claude-task-master/blob/main/CHANGELOG.md)). Spec Kit, OpenSpec and Kiro each keep a single `tasks.md` per change. No source measures per-task files against a checklist, but every tool converged on the list, which tells against the proposal's `tasks/T01-*.md` default.

Context cost explains the retreat. Anthropic's guidance rests on one constraint: "Claude's context window fills up fast, and performance degrades as it fills". It asks for CLAUDE.md files "under 200 lines" and excludes "File-by-file descriptions of the codebase" and "Information that changes frequently" ([best practices](https://code.claude.com/docs/en/best-practices); [memory](https://code.claude.com/docs/en/memory)). The memory docs also note that an instruction in words to read another file is advisory: "Claude sees `AGENTS.md` only if it decides to open the file" ([memory](https://code.claude.com/docs/en/memory)). The ETH Zurich study found that providing context files "does not generally improve task success rates, while increasing inference cost by over 20% on average". Repository overviews in particular "are not helpful", while instructions on non-standard practices are followed ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). Cline's Memory Bank tells the agent to "read ALL memory bank files at the start of EVERY task", yet one user saw a model skip reading it entirely ([Cline](https://docs.cline.bot/prompting/cline-memory-bank); [kangax](https://kangax.substack.com/p/memory-bank-and-the-many-failures)). For the blueprint, this means a short agenda is the only file worth loading every session. Decisions, above all negative ones, are the content agents need most. `design/` is read on demand, never as a whole.

A few ideas from these tools are worth taking without the tools. The most useful comes from OpenSpec. Its merge is mechanical because each requirement is a heading with a stable name. A delta targets that heading, `MODIFIED` carries "the full new version", and `REMOVED` comes "with a line on why" ([OpenSpec writing specs](https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md)). OpenSpec also gives the cleanest content rule: "If implementation can change without changing externally visible behavior, it likely does not belong in the spec" ([concepts](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)). Changes without spec deltas set `skip_specs: true`, and `validate --archived` checks that every task box is ticked ([CLI](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md)). Smaller borrowings: Kiro tags each task with the requirements it serves ("Requirements: 1.1, 2.3") ([Kiro](https://kiro.dev/docs/specs/feature-specs/)). Spec Kit caps `[NEEDS CLARIFICATION: …]` markers at three per spec ([Spec Kit](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)). EARS sentences ("WHEN
<trigger> … the system SHALL <response>") suit state-heavy areas, but Kiro's payoff, property-based tests derived from
them, does not exist without Kiro ([EARS](https://en.wikipedia.org/wiki/Easy_Approach_to_Requirements_Syntax)).

## Documentation frameworks are checklists for design/, not folder layouts

None of the four frameworks should shape the blueprint's folders. Each sharpens one part of it. Diátaxis sorts reader-facing docs into tutorials, how-to guides, reference and explanation ([Diátaxis](https://diataxis.fr/)). An explainer such as `how-it-works.md` is Diátaxis "explanation": it should "explain *why* things are so - design decisions, historical reasons, technical constraints" and be "closely bounded", because instructional and reference material creeping in "interferes with the explanation itself" ([Diátaxis explanation](https://diataxis.fr/explanation/)). The agenda, notes, research, decisions and PRDs are working records, not documentation for a reader with a task, so applying the four types to the whole blueprint would be a category error. They apply to `design/` (area docs as reference, explainers as explanation) and to the published `docs/`.

arc42 is a twelve-section template whose own FAQ says "Please don't *fill in everything*". Its suggested minimum is three to five quality goals as scenarios, the context and external interfaces, a brief solution strategy, the building block view at level 1, and the key crosscutting concepts ([arc42 B-1](https://faq.arc42.org/questions/B-1/); [B-4](https://faq.arc42.org/questions/B-4/)). Section 9 is where decisions go, ideally as ADRs, and it advises "Avoid redundant texts" by pointing back to the strategy section ([arc42 §9](https://docs.arc42.org/section-9/)). That minimum is a good coverage checklist for `design/README.md` and `how-it-works.md`. C4 holds that "the system context and container diagrams are sufficient for most software development teams" and advises against code-level diagrams for long-lived documentation ([C4 diagrams](https://c4model.com/diagrams); [C4 code](https://c4model.com/diagrams/code)). Mermaid's C4 syntax is still "experimental" ([Mermaid](https://mermaid.js.org/syntax/c4.html)). Plain Mermaid flowcharts and sequence diagrams render natively in GitHub markdown and need no build step ([GitHub](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)).

matklad's ARCHITECTURE.md guidance is the most useful rule set for keeping `design/` from going stale. Its premise is that a newcomer needs 2x more time to write a patch but "10x more time to figure out *where* you should change the code". It asks for a short bird's-eye view and a coarse codemap, invariants stated explicitly ("often … expressed as an *absence* of something"), and modules that are named but not linked, because "links go stale". Most importantly: "Don't try to keep it synchronized with code", and revisit it "a couple of times a year" ([matklad](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html)). rust-analyzer's architecture doc follows this shape with inline "Architecture Invariant" callouts ([rust-analyzer](https://rust-analyzer.github.io/book/contributing/architecture.html)). Together with Google's no-schemas rule and OpenSpec's behaviour test, this gives `design/` a clear content boundary: contracts, invariants, structure and reasons, never what the code already says. Coarse descriptions also make the "same commit" sync rule cheap, because most code changes leave them untouched.

For the line between blueprint and user docs, docs-as-code gives the mechanism and PEP 1 gives the policy. GitLab "strongly encourages including documentation in the same merge request as the code" and lets teams make that mandatory ([GitLab](https://docs.gitlab.com/development/documentation/workflow/)). PEP 1 keeps formal documentation outside the proposal ([PEP 1](https://peps.python.org/pep-0001/)). The research found no project that generates user docs from internal design docs. The pattern everywhere is separation plus manual derivation. A workable split under "one home per fact": user-visible facts (CLI flags, config keys) live in `docs/` and the design links to them; internals and reasons live in `design/`; explainers are the source for "About …" explanation pages; tutorials and how-tos are written fresh.

## One small script does what the off-the-shelf validators would

There is no maintained, popular command-line tool that validates markdown front matter against a schema. The remark plugin for it last released in October 2023 ([remark-lint-frontmatter-schema](https://github.com/JulianCataldo/remark-lint-frontmatter-schema)), and Vale lints only string-valued fields, as prose ([Vale](https://vale.sh/docs/formats/front-matter)). Projects with structured design documents write their own. Python's `check-peps.py` is a stdlib-only script with a `REQUIRED_HEADERS` set and an allowed-status list. It prints `filename:line: message` and exits 1 ([check-peps.py](https://github.com/python/peps/blob/main/check-peps.py)). Kubernetes runs `kepval` in CI ([kepval](https://github.com/kubernetes/enhancements/blob/master/docs/kepval.md)), and MDN uses an AJV-based front matter linter ([MDN](https://github.com/mdn/content/tree/main/scripts)). For a few required keys and a status enum, a Python dict is simpler than JSON Schema. `uv` runs a single-file script with inline PEP 723 dependencies, so the validator needs no project or virtualenv ([uv](https://docs.astral.sh/uv/guides/scripts/)). One trap: PyYAML resolves an unquoted `created: 2026-10-07` to a date object, not a string, so the script must accept both ([PyYAML](https://pyyaml.org/wiki/PyYAMLDocumentation)).

The same script can check links and IDs. lychee with `--offline --include-fragments` checks local files and heading anchors with no code ([lychee](https://github.com/lycheeverse/lychee)), while markdownlint's MD051 checks same-file anchors only ([MD051](https://github.com/DavidAnson/markdownlint/blob/main/doc/md051.md)). GitLab draws the useful line: its link job checks relative links and anchors and skips "any link that requires a network connection" ([GitLab testing](https://docs.gitlab.com/development/documentation/testing/)). External URLs belong in an occasional manual run. Every ID-linking system found (Foam wikilinks, MyST targets, mkdocs-autorefs) needs a renderer or an editor extension to resolve its links, and Dendron has been in maintenance mode since February 2023 ([Foam](https://docs.foamnotes.com/features/wikilinks/); [MyST](https://mystmd.org/guide/cross-references); [Dendron](https://randomgeekery.org/post/2023/02/dendron-is-officially-in-maintenance-mode/)). Plain-text `(D201)`, `(P3)` and `(P3/T2)` resolved by a regex pass work everywhere, including in a terminal, provided the scan skips fenced and inline code.

Generated regions with a check mode are a solved pattern. cog has `--check`, doctoc's `--dryrun` exits 1 when files need updating, and mdsh has `--frozen` ([cog](https://cog.readthedocs.io/en/latest/running.html); [doctoc](https://github.com/thlorenz/doctoc); [mdsh](https://github.com/zimbatm/mdsh)). Each one regenerates the region in memory and compares. Because the index rows come from front matter and headings the validator already parses, writing `index --check` in the same script avoids parsing every file twice. Dates are the exception. Every static site generator that shows "last updated" runs `git log` at build time and warns that shallow clones give wrong dates ([Hugo](https://gohugo.io/methods/page/gitinfo/); [mkdocs plugin](https://github.com/timvink/mkdocs-git-revision-date-localized-plugin)). Writing git dates into a committed index is also circular: the commit that edits a document makes that document's index row stale, because the commit's own date is unknown until after the commit. The proposal's PRD index has a "last update" column, so that column should be computed when viewed, with `git log -1 --format=%as`, not committed ([git](https://git-scm.com/docs/pretty-formats)).

The pre-commit framework's main benefits, filtering by file and managing tool environments, do not help a validator that must see the whole repository to resolve cross-file IDs ([pre-commit](https://pre-commit.com/)). A committed `.githooks/pre-commit` enabled with `core.hooksPath`, calling the same command that CI runs, is the smallest setup ([githooks](https://git-scm.com/docs/githooks)). The caveat is that a plain hook checks the working tree rather than the staged snapshot. That is acceptable for one person, with CI as the backstop once the blueprint is public. prek is the upgrade path if a pre-commit config is ever wanted, without the Python runtime ([prek](https://prek.j178.dev/)).

## Conclusion and prioritised recommendations

The sources point to a different main risk than missing structure. The blueprint's failure modes are facts stored in two places and lifecycle promises with no check behind them. Each failure documented above is one of these: markdown volume (Spec Kit), two copies drifting apart (Rust RFCs against the Reference, BMAD's drifted status file), or a status nobody updates (Cameron's "impossible to tell … whether it was implemented"). Two working rules follow. Store each fact once and generate everything derivable. Tie each status change to something the script can verify. The proposal already states the first rule, but several of its own front matter keys break it (`id` repeats the folder number, `decisions` and `research` repeat inline references, `in_progress` repeats the PRDs' statuses).

The evidence base is thinner than the tooling noise suggests. No controlled study compares per-task files with checklists, many decisions per file with one per file, or hand-run delta merges with OpenSpec's CLI. The agent-specific advice on decision records is 2026 practitioner and vendor opinion. Treat the recommendations below as reversible, and review them after the first two PRDs have gone from draft to implemented. Within each group they are in priority order. Across groups, Change 1–3 matter most.

### Keep

**Keep 1. PRDs as frozen history, `design/` as the only current truth.** This is the PEP 1 and OpenSpec model, and the model Rust had to retrofit with RFC 1636 ([PEP 1](https://peps.python.org/pep-0001/); [RFC 1636](https://rust-lang.github.io/rfcs/1636-document_all_features.html); [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)). State the persistence model once in `blueprint/README.md`, as Spec Kit advises teams to do ([Spec Kit](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md)). Grow `design/` areas only when work touches them, as OpenSpec's brownfield guidance does ([OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md)).

**Keep 2. Short decision entries with global IDs, in themed files, cited only by ID.** Status comes from the relationship notes, with no separate field. This matches adr-tools' notes in the Status section and MADR 4.0's identifier-only status ([adr-tools](https://github.com/npryce/adr-tools/blob/master/tests/linking.expected); [MADR](https://github.com/adr/madr/blob/develop/CHANGELOG.md)). Themed files lack precedent but cost nothing as long as no link targets a file or a heading slug.

**Keep 3. Only agreed decisions become entries; proposals stay in discussion notes.** This is Spotify's RFC-then-ADR split ([Spotify](https://engineering.atspotify.com/2020/04/when-should-i-write-an-architecture-decision-record)). Add one line to CLAUDE.md or AGENTS.md saying that notes are not decisions, so agents don't act on unagreed ideas.

**Keep 4. Generated indexes in marked regions, plus one validator as hook and CI.** This is the check-peps pattern with cog-style check mode ([check-peps.py](https://github.com/python/peps/blob/main/check-peps.py); [cog](https://cog.readthedocs.io/en/latest/running.html)). Each index row should carry a one-sentence summary taken from the document's first line, so an agent can choose what to open, as Agent OS's standards index does ([Agent OS](https://github.com/buildermethods/agent-os/blob/main/commands/agent-os/index-standards.md)).

**Keep 5. A short agenda as the session entry point.** It plays the role of Cline's `activeContext.md` and `progress.md` and of Anthropic's progress file ([Cline](https://docs.cline.bot/prompting/cline-memory-bank); [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). It is the only blueprint file small enough to import every session.

**Keep 6. Strands as folders, documents inside starting as files, explainers inside `design/`, private by default.** Folders from the start keep strand paths stable. Explainers are Diátaxis explanation, and the area docs win any disagreement ([Diátaxis](https://diataxis.fr/explanation/)). Oxide also keeps its RFD content in a private repository with access control ([rfd-site](https://github.com/oxidecomputer/rfd-site)).

### Change

**Change 1. Make `implemented` a gate, not a label.** A PRD becomes `implemented` only once its delta has been reconciled with what actually shipped and merged into `design/` in the same commit, a short "As shipped" note records any deviations, and one banner line under the title reads "Historical. Current design: `design/<area>`". This combines OpenSpec's archive rule, Rust's stabilisation gate, PEP 12's banner and the fix for Cameron's complaint ([OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/editing-changes.md); [PEP 12](https://peps.python.org/pep-0012/); [Cameron](https://www.ncameron.org/blog/the-problem-with-rfcs/)). The validator can enforce part of it: an implemented PRD has the banner and no unchecked tasks, which is OpenSpec's `--archived` check ([CLI](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md)).

**Change 2. Make the design delta addressable.** Give `design/` files stable `##`/`###` headings, one concept each, and write the delta in three forms only: `MODIFIED <path> § <heading>` with the full replacement text and a "Previously:" line, `ADDED` with the new section, and `REMOVED` with a reason. A `design_delta: none` flag lets a refactoring PRD skip the delta legitimately. Without stable headings, "merge the delta" turns into free-form rewriting ([OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md)). An example:

```markdown
## Design delta

### MODIFIED design/sidebar/groups.md § Group headers

<full new text of the section>

Previously: headers showed the branch name only.

### REMOVED design/sidebar/groups.md § Manual ordering

Reason: replaced by worktree order (D212).
```

**Change 3. Tasks start as a checklist in the PRD's README, not as `tasks/T01-*.md` files.** Use lines such as `- [ ] T2: … — done when: … (§ Group headers)`. `(P3/T2)` stays resolvable, and a task becomes its own file only when it needs notes or a tracker link. Spec Kit, OpenSpec, Kiro and Task Master all converged on one list, and Anthropic's harness uses one feature list ([Task Master](https://github.com/eyaltoledano/claude-task-master/blob/main/CHANGELOG.md); [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Defer the `tracker` modes until a real tracker exists.

**Change 4. Five PRD statuses: draft, accepted, implemented, rejected, superseded.** Drop `in-progress`: KEPs, Swift and Oxide do without it, and the checklist already shows progress ([RFD 1](https://rfd.shared.oxide.computer/rfd/0001); [KEP-0000](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md); [Swift](https://github.com/swiftlang/swift-evolution/blob/main/process.md)). `rejected` absorbs withdrawn and abandoned, because the author is also the decider. Following Shape Up, reject drafts that sit untouched instead of keeping them as a backlog ([Shape Up](https://basecamp.com/shapeup/2.1-chapter-07)).

**Change 5. Cut front matter to facts with no other home.** Drop `id`, which repeats the folder or file number; `decisions` and `research`, which repeat inline `(D7)` references and paths that the generator can list; `in_progress` on `design/README.md`, which can be derived from accepted PRDs; and `tracker`, until a tracker exists. `title` and the H1 state the same fact twice, so keep one or have the validator check that they match. Keep status only where it changes how far a reader should trust the document: PRD, research (`current`/`outdated`), design area and explainer, and task files when they exist. Drop `living`, `designing/building/maintaining` and the notes' `open/closed`, since the agenda already holds topic state. Quote dates or accept date objects ([PyYAML](https://pyyaml.org/wiki/PyYAMLDocumentation)). A minimal PRD header:

```yaml
---
title: Worktree groups
status: accepted        # draft | accepted | implemented | rejected | superseded
created: "2026-10-06"
parent: null
design: [sidebar/groups, api/workspaces]
superseded_by: null
---
```

**Change 6. Give each decision a cost, and make supersede links reciprocal and checked.** Add a one-line **Cost** (the Y-statement's "accepting that"). Expect **Not chosen** whenever a real alternative was weighed ([Zimmermann 2026](https://ozimmer.ch/practices/2026/09/12/ADRMistakes.html)). The new entry declares `Supersedes (D201)`, and the validator requires the matching "Superseded by (D230)" note on D201, which closes the two-live-rules gap that agents fall into ([dev.to](https://dev.to/naman_here/adrs-for-ai-coding-agents-how-to-make-every-agent-read-architecture-decisions-3he4)). Keep the vocabulary to three fixed pairs (Supersedes/Superseded by, Details/Detailed by, Amends/Amended by), and use "Amended by" only for small additions that leave the decision intact ([Fowler](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html)).

```markdown
## D230: The MCP server lives in the daemon (2026-10-12)

> Supersedes (D201).

**Decision:** …

**Why:** … agreed in [notes 09](../notes/09-mcp.md).

**Cost:** the daemon gains a dependency it must keep secure.

**Not chosen:** a separate MCP process, because …
```

**Change 7. Keep git dates out of committed indexes.** Remove "last update" from the generated PRD index and show it only through a `status` command at view time, using the author date (`%as`) ([git](https://git-scm.com/docs/pretty-formats); [Hugo](https://gohugo.io/methods/page/gitinfo/)).

**Change 8. Write the content rules for `design/` down.** State invariants, including absences; name modules rather than linking them; never paste schemas or code; keep user-visible facts in `docs/` and link to them; and review explainers on a fixed cadence instead of syncing them with every commit. These come from matklad, Ubl and OpenSpec ([matklad](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html); [Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/); [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)). Once PRDs exist, the `proposed` status in `design/` should apply only to greenfield areas. Planned changes to built areas belong in PRD deltas.

**Change 9. A 1–3-page PRD template in which only Problem and Design delta are required.** Optional sections: Appetite and No-gos ([Shape Up](https://basecamp.com/shapeup/1.5-chapter-06)), Non-goals and Alternatives ([Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/)), files and interfaces involved, and an end-to-end verification step ([Anthropic](https://code.claude.com/docs/en/best-practices)). Allow at most three `[NEEDS CLARIFICATION]` markers while the PRD is a draft ([Spec Kit](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)). Write the threshold into the blueprint README: if the diff fits in one sentence, or doing it is faster than writing it up, there is no PRD ([HashiCorp](https://www.hashicorp.com/en/how-hashicorp-works/articles/writing-practices-and-culture)).

**Change 10. Wire agents with a pointer and a skill, not a load-everything rule.** AGENTS.md says when to consult the blueprint if it is present. Procedures (start a PRD, merge a delta, regenerate indexes) go in an on-demand skill ([memory](https://code.claude.com/docs/en/memory)). Test retrieval from a fresh session. The research did not establish whether an `@` import of a git-ignored file that is absent fails silently, so keep the pointer in words.

### Drop

**Drop 1. Adopting any spec-driven or ADR toolkit.** That covers Spec Kit, Kiro, BMAD, Agent OS, Task Master, adr-tools and log4brains. Each assumes one file per decision or its own folder schema, and several are stale or shrinking ([adr-tools](https://github.com/npryce/adr-tools); [BMAD](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)).

**Drop 2. Per-change file fan-out, approval gates, personas and per-task reports.** These are the sources of the 2,577-line and 1,300-line counts ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html); [Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)), and Agent OS removed them as "Too complex" ([Agent OS](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)).

**Drop 3. Read-everything rules and file-by-file overviews.** They add cost without improving success ([ETH](https://arxiv.org/abs/2602.11988); [Anthropic](https://code.claude.com/docs/en/best-practices)).

**Drop 4. Schema languages and renderer-bound linking.** That means JSON Schema, the remark stack, Vale, wikilinks, MyST and Structurizr while the front matter stays flat ([remark plugin](https://github.com/JulianCataldo/remark-lint-frontmatter-schema); [Dendron](https://randomgeekery.org/post/2023/02/dendron-is-officially-in-maintenance-mode/)). Keep external link checks with lychee out of the hook and run them by hand ([lychee](https://github.com/lycheeverse/lychee)).

**Drop 5. Mandatory EARS or SHALL/Scenario phrasing everywhere.** Use it only for state-heavy areas such as agent detection or the pane lifecycle ([EARS](https://en.wikipedia.org/wiki/Easy_Approach_to_Requirements_Syntax); [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)).

**Drop 6. Diagrams below container level.** One context diagram and one container diagram, in plain Mermaid inside `how-it-works.md`, are enough ([C4](https://c4model.com/diagrams); [Mermaid C4](https://mermaid.js.org/syntax/c4.html)).
