# Notes: the initial design

How skillbook's initial design was discussed, from 2026-10-07 to 2026-10-10, in one long session between the person and an agent. The discussion started inside herdsman, the person's fork of herdr, and moved here when skillbook was created. Decisions are recorded in [decisions.md](../decisions.md); this file keeps the path to them.

## The blueprint, first shape (2026-10-07)

- **Starting point:** the person's way of working, where an idea document grows into design, decisions and research documents, kept in step with the code; with the worry that such documents are private.
- **Agreed:** two kinds of documents (user docs in the repository, project docs private by default); a private blueprint kept in its own repository and cloned into the project; PRDs as sub-designs whose changes merge into the design; folders per PRD; numbered decisions; the name "blueprint".
- **Example studied:** trailscout's design docs, an earlier project's working example, showed an agenda, discussion notes, themed decision files and an overview that tells the design as a story.
- **Research:** how design documentation is organised elsewhere (design-documentation-approaches). Its advice: keep the skeleton, cut the ceremony; generated indexes, a gate when work is implemented, addressable design changes.
- **Open:** tasks; the person was unsure between a checklist and one file per task.

## The blueprint, restructured (2026-10-08)

- **Questions:** 1 the roadmap; 2 files or folders first; 3 numbers in file names; 4 tasks; 5 requirements; 6 PRDs as small blueprints.
- 1, roadmap: replaces the agenda (D2).
- 2 and 3: everything starts as a file and becomes a folder; READMEs hold the order and act as maps; no numbers in file names (D2).
- 4, tasks: one file per task, with the fields an agent needs (D8).
- 5, requirements: a strand of its own, current truth like design.
- 6, PRDs become **workstreams**: contained parts of the work with the same strands as the blueprint, nested, merged back into their parent (D5).
- **Added by the person:** top-down work and two-way sync between blueprint and code as principles (D3, D4); a section on how an agent uses the blueprint while developing.

## Parallel work and consolidation (2026-10-09)

- **Gaps reviewed one by one:** parallel agents, finding the code, existing projects, publishing, the agent pointer, a worked example, the script.
- Parallel agents: like code, one agent per file; workstreams split the work; three modes (direct, staged with `pending/`, branched) (D7).
- IDs: workstream keys as prefixes rather than hashes, so merges stay easy to follow (D5).
- Consolidation: named, so it is never confused with a git merge; completion can be forced by the person; parents' changes reach their children as notes; the "Previously:" check suffices; attachments are the person's call (D6, D9).
- No script: the person preferred a design that needs none; nothing is generated (D10).
- Existing projects, publishing, pointers, user docs: decided as D11–D14.
- **Worked example:** herdsman's worktree groups, written as design/blueprint-example.md; it added "Taken up in" for ideas and drafts that hold their own discussion.

## greenrepo (2026-10-09 to 2026-10-10)

- **Starting point:** a document describing everything a good repository needs, which later becomes a skill.
- **Research:** seven researchers on standards, CI, releases, documentation, stacks and reference repositories (open-source-repository-standard).
- **Draft 1** had three levels anchored to the OpenSSF Baseline. The person questioned each level in turn: private repositories need the same rules, solo repositories also release. Levels were replaced by a core plus conditions, with visibility out of the rules (D15).
- **Reviewed part by part:** community, documentation (a getting-started guide as simple as possible, one install page, user docs on GitHub Pages, docs never relying on the blueprint), agents, code quality, CI, releases (web and mobile delivery covered), dependencies, settings (squash merging by default), upkeep.
- **Profiles:** the person asked for greenrepo to stay generic, with specifics only where valuable (D16).
- **Upkeep automation:** the person asked how agents and bots keep a repository healthy; a second research round (repository-health-automation) led to the health issue, committed expected settings, renewals and deviations, and agents run by hand first (D18, D19).
