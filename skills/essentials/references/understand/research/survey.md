# understand-research-survey

## Purpose

Finds existing candidates and compares them on common terms, without taking over the caller's choice.

## When to use

Use when the user needs to know what already exists on a subject, compared on the same terms, such as existing tools, papers or alternatives. Read it whenever you are asked which options of some kind exist, or which ones a set of notes or pages covers, and how they compare, even when every option is in the user's own files.

## When not

- Inventing options: use the `understand-brainstorm` guide. A survey finds options that already exist.
- Choosing between known options: use the `understand-weigh` guide. The survey supplies the comparison, not the choice.
- One fact about a candidate: use the `understand-research` guide's "Check a fact" part. A field-wide comparison is not needed.

## Gives back

Candidates compared on the same terms, with sources, excluded and unexamined candidates, search coverage and dates, in this default shape:

```text
Scope:         what counts, what doesn't
Terms:         what each candidate is compared on
Comparison:    each fully compared candidate on each term, with its evidence or "not found"
Screened out:  each candidate left out, with why
Coverage:      where you searched, what you did not search, the survey's date and each source's date
```

## Rules

1. **Set the scope and comparison terms before you search.** Terms chosen afterward favor the first candidates found. Reuse the caller's criteria or current frame. Otherwise follow the `understand-frame` guide and the main skill's step 1 on who decides.
2. **Search widely before you examine candidates deeply.** The most visible candidate need not be the best. Use several relevant kinds of source where available. Report unavailable coverage; do not invent breadth.
3. **Compare every fully examined candidate on every term.** Give evidence or "not found" for each value. Use no guess or score without a meaningful measure.
4. **Name screened-out candidates with their reasons.** A names-only list is not a completed comparison or an evidence-backed rejection. List an unexamined long tail separately as not compared, with the reason and coverage limit.
5. **Treat the user's own option like every other candidate.** Favoring one candidate hides information needed for the later choice. Give each candidate's supported strengths and weaknesses.
6. **Report search coverage and its date, in a Coverage line that ends the answer.** Without it, a short list reads as everything that exists, and old notes read as current. A survey is a snapshot, not proof that nothing else exists.
   - In the line, give where you searched and at least one kind of source you did not search, even when the user limited where to look. Give each source's own date, or say it has none, and the date you searched.
   - Look for a date in every file you read, a README included, before you write the line.
   - Say what remains unverified.
   - For example: "Coverage: the three supplier price lists in quotes/, dated 3 March. Not searched: the suppliers' current sites, trade directories or suppliers not in the folder."
   - When the same answer goes on to a choice, put the Coverage line just before the recommendation. The choice ends the answer, by the `understand-weigh` guide's rule 5, because a question placed above a footnote is easily missed.
7. **Add no survey-only approval checkpoint.** A survey reads and compares. It changes nothing. Ask first only for a choice the user owns, by the main skill's step 1 on who decides, or for a worker cost that needs approval, by the `coordinate-delegate` guide's rule 8. Then end the turn. Otherwise put the scope, the terms and how you searched in the final answer.
8. **Return the comparison to its active caller.** That is the guide or task that asked for the survey, and it owns the choice. When the user asked you to choose, compare the candidates with the `understand-weigh` guide after the survey. When the `understand-weigh` guide asked for this survey, return to it; do not start it again. Start no new candidate generation. A request for existing options alone starts no choice round and gets no recommendation.

## Advice

- A theme supported by fewer than about three independent origins is an anecdote worth investigating, not an established general finding. Apply this as guidance, with evidence quality and limits, not a vote by source count.
- Report notable absences with where you looked.
- Refresh an earlier survey by reporting what changed since its date. Do not treat old values as current just because the update is narrow.

## Instructions

Find existing candidates and compare them on terms chosen before the search. Keep excluded candidates apart from ones you have not examined, so the caller can see what the survey actually covers. **Set scope, search wide, screen, then compare and return the evidence without taking over the caller's choice.**

1. **Set scope and comparison terms under rule 1.** Terms chosen after seeing candidates can favor the most visible one and waste the caller's later comparison.
   - Use the `understand-frame` guide for missing terms, and the `understand-clarify` guide for consequential questions the user owns.
   - Start without an approval step, by rule 7. Ask first only for a choice the user owns or a worker cost that needs approval. Then end the turn.
2. **Search wide before deep, by rule 2.** Deep reading of the first candidate can hide better options elsewhere.
   - Search several relevant kinds of source where available. Treat earlier lists and comparisons as leads to recheck, not findings to repeat unchecked.
   - Search serially, unless separate large parts remain after narrowing. For those, use the `coordinate-delegate` guide with the `coordinate-delegate-fanout` guide. Preserve its limits and validation states.
3. **Screen candidates against scope, by rule 4.** A silent omission can look like an evidence-backed rejection.
   - Name each excluded candidate and its reason, and list the unexamined long tail apart, by rule 4.
   - Fully compare a useful handful by default. Stop when new searches only return candidates already found, and report that actual limit.
4. **Compare every examined candidate on every term, by rules 3 and 5.** Unequal terms or favoritism hide information the user needs for a later choice.
   - Give evidence or "not found" for every value, the user's own option included.
   - For each compared candidate, explain who it suits and who it does not.
   - Treat themes with few independent origins as anecdotes to investigate, not a vote.
   - Use a short table or list that fits the medium. When you refresh a survey, report changes and recheck facts needed for the current answer.
5. **Return the comparison to its owner under rules 6–8.** A survey that silently chooses can bypass the caller's decision and hide incomplete coverage.
   - Give scope, terms, comparison, exclusions and unexamined candidates. Add these to the parent's result shape.
   - End the survey with the Coverage line of rule 6, even for a short comparison from the user's own files. When a choice follows in the same answer, the choice comes last, by rule 6.
   - For a direct request that includes choosing, use the `understand-weigh` guide after the comparison, by rule 8.
   - Keep lasting records with their owner.
6. **Check the survey and "Gives back" before returning it.** Always do this last. A names-only list cannot stand in for a completed comparison.
   - Check common terms, traceable evidence, honest gaps, exclusions, unexamined candidates, negative results, coverage and dates. Preserve actual validation states.
   - Fix missing values or overstated coverage before returning, under the `understand-research` guide's final step. Leave the choice with its owner.
