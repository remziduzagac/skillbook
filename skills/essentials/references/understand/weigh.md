# understand-weigh

## Purpose

Compares named options on common terms and recommends one, or says what would settle the choice.

## When to use

Use when two or more named options need comparison and a recommendation. A requested debate is one example.

## When not

- One option or a settled choice to check: use the `understand-challenge` guide for weak points. There are no alternatives to compare.
- No options yet: use the `understand-research-survey` guide to find options that already exist, or the `understand-brainstorm` guide to invent new ones. A comparison needs named options.
- A fact that would decide the choice: use sources or a test. Scoring options cannot establish the fact.
- Independent agents gave different answers: keep each answer and the disagreement. Use this comparison only if the user asks for a recommendation.

## Gives back

A comparison and recommendation, or no clear winner with what would settle it. Return options needing more development to the task that asked; do not start another brainstorm. The skill that saves records gets the comparison, why the chosen option won and the options set aside.

```text
Terms:         what matters to the question
Options:       each one's values on the terms, then its benefits, costs, risks and unknowns
Dropped:       excluded options and reasons
Recommended:   why it beats the next best; easy or hard to undo; or no clear winner
Would change:  unknowns and what would settle them
```

Lay it out by term: one row or list item per term, with every option's value on it, such as a short table with a column per option. A relative value, such as "half the price of B", gives the term for both. A term given for one option only hides how the other compares. Use the `respond-layout` guide for the form.

## Rules

1. **Compare every option on every term.** Different terms cannot support a comparison.
   - Drop an option that breaks a constraint, and name the constraint. If the user named that option, still give its values on the terms, so they can see why it lost. A dropped option needs no risks or unknowns.
2. **Give benefits, costs, risks and unknowns for each option.** Values on the terms are not enough: risks and unknowns show what could go wrong. Search for real downsides. If you find none within the terms, say where you looked. A forced downside invents evidence, and an unexamined option hides costs.
3. **Name unknowns that could change the recommendation, each with what would settle it.** Use the `understand-research` guide or a permitted test for deciding facts, and the `understand-clarify` guide for the user's preference. A cost or risk that holds only if something is true is an unknown too, such as a parking permit needed only if the site has no spaces: say how to find out whether it applies.
   - When the user asks which to pick, compare and recommend before you ask about their preference. Recommend under the likelier reading, and name the preference with the pick it would change, such as one bike unless they often ride on gravel. Asking first leaves the user with questions and no comparison to answer them from.
   - With no likelier reading, give "no clear winner" and the question that settles it, by rule 4.
   - This varies the `understand` guide's who-decides rule for a pick the user asked for: the preference stays theirs, and the answer still asks about it, after the comparison and a pick.
4. **Recommend with why it beats the next best, or say "no clear winner".** Give what would settle a tie. Giving no recommendation leaves the decision undone. Forcing a recommendation hides a tie.
5. **Follow the `understand` guide's who-decides rule.** When a caller asks for a comparison, return it without starting that caller's choice round. When the user asks directly, end with their choice in the `respond-ask` guide's form: a line starting "Recommended answer:" with the option and the reason, or "No recommended answer:" with why. A "yes" then accepts the pick when work follows. Apply the shared rule to agent-made choices. A bare choice cannot be judged.

## Instructions

Compare named options on common terms and recommend one, or explain what would settle a tie. Evidence and an honest search for downsides matter more than a score that merely looks exact. **Set the terms first, compare every option, then return the recommendation or unresolved choice.**

1. **Set comparison terms from the `understand-frame` guide before scoring.** Terms chosen after a favorite appears can make the comparison justify it rather than test it.
   - Reuse the frame's good-answer terms, otherwise what matters to the question.
   - Find the constraints before you compare: read the request and the project's own files for limits, such as the platforms it must run on or a rule in its instructions. Drop options that break one, by rule 1. A constraint you never looked for cannot drop anything.
   - Scale depth with the `act-stakes` guide. Include the cost of being wrong and how easily the choice can be undone.
2. **Compare every option on every term, by rules 1 and 2.** Unequal scrutiny can make the least examined option look safest.
   - Lay it out by term, with every option's value on each, as "Gives back" shows.
   - Give benefits, costs, risks and unknowns, including later costs. Search for real downsides; if none is found, say where you looked rather than inventing one.
   - At high stakes or for a requested debate, put each option through the `understand-argue` and `understand-challenge` guides, to equal depth. Reuse a challenge only by the `understand-challenge` guide's rule 7. Use each challenge's verdict in this comparison, and keep it out of the case it tests.
   - Use scores or weights only when the measure means something. Words usually say more than an unsupported number. A short table or list may carry the comparison.
3. **Resolve or name deciding unknowns under rule 3.** A missing fact or user preference can reverse the recommendation after the user relies on it.
   - Use the `understand-research` guide or a permitted test for facts, and the `understand-clarify` guide for the user's preference. Give what would settle each gap, including a cost that holds only if something is true.
   - For a pick the user asked for, recommend first and name each preference with the pick it would change, by rule 3.
   - Use survey findings in this comparison. Return options that need more work, or a combination worth developing, to the task that asked. Do not start a new brainstorm from here.
4. **Return the recommendation or tie under rules 4 and 5.** A winner without a reason cannot be judged; forcing one conceals a real tie.
   - Explain why it beats the next best, or give “no clear winner” with what would settle it. Include exclusions and what would change the result.
   - Return a caller's comparison without starting its choice round. For a direct request, end with the "Recommended answer:" or "No recommended answer:" line, by rule 5. Preserve council disagreements.
5. **Check the comparison and “Gives back” before returning it.** Always do this last. The caller needs a grounded basis for choice, including its limits.
   - Check common terms, evidence, downside searches and current challenges. Return a recommendation, a tie or a specific development need preventing comparison.
   - Check each deciding unknown has what would settle it, by rule 3.
   - Check that every term has every option's value, and that a direct request ends with the labelled line, by rule 5.
   - Fix unsupported or unequal parts before returning under the `understand` guide's rules. Leave decisions and lasting changes with their owner.
